    2. Where the kiosk fleet view lives: Kiosks, with one pointer from System¶

    Decision: in Kiosks, not System. System is about this server (its version, its restart, its backups). Kiosks is already the per-device home: the cards there have the online dot, last seen and the Update button. A second fleet list in System would duplicate state and controls. Instead:

    • Kiosks gets a "Kiosk software" summary at the top of its list, versions on every card, and fixed states (§3.1–3.2).
    • System › Updates gets one pointer row, shown only while at least one kiosk can be updated (§3.4).

    3. Spec¶

    3.1 Kiosks › "Kiosk software" summary row¶

    Placed in KiosksSettings.vue inside SettingsSection id="kiosks-list", above the kiosk cards and below the intro or "+ Add kiosk" button. It is a SettingRow (existing shell component).

    Shown only when at least one registered kiosk reports an agent version (k.agentVersion != null). Browser-only kiosks (?kiosk=name) have no agent. With none, the row is omitted, so an all-in-one or browser-only setup sees no noise.

    Inputs: availableVersion from fetchAvailableAgentVersion(), and the kiosks with an agent. Let behind = agent kiosks with agentVersion !== availableVersion that aren't blocked, where blocked means the last update failed because the kiosk's OS is too old (§3.2, "needs a newer OS"). Retrying those can't succeed, so they are never counted or included in Update all. Let updating = kiosks with agentUpdateRequested. When every out-of-date kiosk is blocked, the row shows the "all up to date" state's sibling: No kiosk can be updated right now. {n} need(s) a newer OS first.

    State Label Description Control
    Manifest not loaded yet Kiosk software Checking for updates… none
    Manifest failed (availableVersion == null after load) Kiosk software Couldn't check for kiosk updates. The kiosks keep working. Try again (.btn)
    All up to date Kiosk software All kiosks are up to date ({v}). none
    Some behind, none updating Kiosk software {n} of {total} kiosks can be updated to {v}. (1 → 1 kiosk can be updated to {v}.) Update all (.btn--primary)
    Updating Kiosk software Updating {n} kiosk(s)… They restart their screen when done. Update all, disabled, label Updating…
    • {v} = the available version, shown as the first 7 characters in --font-data (versions are commit hashes). {total} counts only agent kiosks.
    • Update all calls store.triggerUpdate(id) for each kiosk in behind that is online. Offline ones get the request too: the flag waits for their next poll, as today. The row then refreshes the list. No confirmation, because updates are safe (rollback is automatic).
    • If any triggerUpdate rejects: a notify error toast Couldn't start the update on {id}. The others continue.

    3.2 Kiosk card: version line and update states¶

    Each kiosk-card keeps its layout (id, online dot, hostname · seen). A third meta line is added under kiosk-card__meta, in the same style (--fs-sm, --ink-2), only for kiosks with an agent:

    State Version line Button row (existing kiosk-card__update-row)
    Up to date Kiosk software {cur} · up to date none
    Update available Kiosk software {cur} · {v} available Update
    Requested Updating to {v}… Updating… (disabled)
    Failed: Python too old (agentUpdateStatus starts with error and the message contains python) Kiosk software {cur} · update needs a newer OS in --warn Update hidden. A --fs-sm line: Reinstall this kiosk with a current Raspberry Pi OS, then update.

    No agent (agentVersion == null) no line none

    • The existing "needs OS update" span is removed. The rows above replace it.
    • Backend need (small): the kiosk list must expose the agent's failure message, not just error…. Add agentUpdateMessage (the updater's message field, already written by update-kiosk.sh:268) to GET /api/kiosks. Until it lands, treat every error as "other".
    • Touch: Update, Try again and Update all have min-height: var(--touch-target).
    • Phone width (< 480px): the summary SettingRow stacks (control full width), and the cards already stack.

    3.4 System › Updates: pointer to kiosk updates¶

    Under the existing Updates content, a SettingRow, only while behind.length > 0 (behind as defined in §3.1): - Label Kiosk software. Description {n} kiosk(s) can be updated to {v}. - Control: Open Kiosks (.btn). It routes to /settings?setting=kiosks-software.

    It reads the same kiosks store, so it is never out of sync with §3.1. It doesn't update anything itself.

    4. Container self-restart¶

    Decision (owner, 2026-10-29): A, not built. Containers are restarted from Docker. In a container, System › Restart shows only Reload UI and the one-line Docker pointer (§3.3). Options B and C below are recorded for context and are out of build scope.

    Background. CALVIN_HOST_CONTROL guards actions on the machine (reboot, systemd, the update script, display power). A container's self-exit touches only its own process, so it isn't host control. But it only works if Docker restarts the container, and Calvin can't check that from inside (no Docker socket, by design).

    • docker/docker-compose.yml:23 sets restart: unless-stopped, so compose installs come back.
    • The Unraid template (deploy/unraid/calvin.xml) sets no restart policy (<ExtraParams/> is empty), and its Overview tells users to restart from the Docker tab. A self-exit there could leave Calvin stopped until someone opens Unraid. (Unverified on a real Unraid box: confirm the policy dockerMan applies.)

    Options

    • A. Don't build it (chosen). Containers keep restarting from Docker; §3.3 adds the one-line pointer. Restarts are rarely needed now: plugin installs are live and config is hot.
    • B. (Not built.) Build it behind its own opt-in. A separate setting CALVIN_SELF_RESTART=1, not a host-control exception. It defaults on only in docker/docker-compose.yml (next to restart: unless-stopped). The Unraid template gets it plus --restart=unless-stopped in ExtraParams. GET /api/system/environment adds capabilities.restart_self. POST /api/system/restart-backend in a container then returns 200 and, after the existing _BACKEND_RESTART_DELAY_SEC, sends SIGTERM to its own PID. Code placement: a new require_self_restart() beside require_host_control() in backend/app/utils/host_control.py, so the two guards read side by side and can't be confused. UI: the Restart Calvin server row (§3.3) shows when restart_self is true. Confirm message: Calvin restarts its container. Docker starts it again in a few seconds. If it doesn't come back, start it from Docker.
    • C. (Not built.) Build it with no opt-in. Not recommended: it silently strands Unraid installs that lack a restart policy.
