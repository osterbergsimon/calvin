    Settings copy and knobs audit¶

    Status: spec. Mockup: mocks/settings-copy/settings-copy.html, PNGs mocks/settings-copy/png/c1.png, c2.png. Frontend only, except §2 (scope), which needs an owner decision.

    Every SettingRow, section and option label in Settings was read against what the code actually does. Category structure (CLV-17) stays. This is about the words and the knobs inside it.

    1. Findings, worst first¶

    1. You can't tell which screens a setting changes. Almost every knob is saved on the server and applies to every screen, but several say "this device", "this Pi" or "the Pi's timezone". Touchscreen says "Whether this device is treated as a touchscreen" and then forces touch on every kiosk, phone and laptop. Settings UI size scales Settings on the phone and the wall alike. This is what caused the photos-fullscreen trap (PR #149).
    2. Some descriptions are wrong.
    3. Photo-frame timeout: "Seconds before the photo frame advances." It is actually the idle time before photo-frame mode starts (usePhotoFrameMode.js). The slider also defaults to 60 while the store defaults to 300.
    4. Display name: "shown in the title bar". It's shown in the clock bar.
    5. Auto-hide delay: "the mode indicator". The section is about key-press feedback.
    6. Engineer words. "Origins", "statusbar items", "Config polling interval", "Backend/Frontend version", "Horizontal/Vertical layout" (meaning top/bottom vs side bars), "Apply display rotation … OS display output", "‹inherited from global›".
    7. Redundant or half-knobs.
    8. Screen timeout toggle + Timeout "(0 = never)": two ways to say off.
    9. Theme mode "Auto" vs "Time": you can't tell which one follows the clock.
    10. Dark mode start/end (hour): number inputs taking 0–23.
    11. Things a family member should never meet sit next to things they use daily. Repository, Branch, Log level, Config polling interval and Console logging sit in the open in System.
    12. Similar names for different things. "Keyboard" (on-screen keyboard) vs "Button bindings" (remote) vs "Key-press feedback". "Photo-frame mode" vs photos "Fullscreen". "Power schedule" (Screen & keyboard) vs "Display schedule" (Kiosks).

    2. Scope: say where a setting applies (owner decision)¶

    Every row says who it affects, using one rule, not ad-hoc copy:

    • Default (no marker): all screens. That's most settings, so no noise.
    • A row that applies only to the browser you're holding gets a scope chip after the label: This screen (--fs-xs, --ink-2, 1px --line border, --radius-sm, padding 0 6px). Its description never repeats "this device".
    • A row a kiosk can override keeps the Kiosks pattern, with new copy (§3.5).

    Decision needed (gate): move the two settings that are obviously per-screen from server config to the browser (localStorage, try/catch, same pattern as calvin-osk-layout):

    Setting Today Proposed Why
    Touchscreen (touchControls) server, all screens This screen (calvin-touch-controls) A mouse PC and a wall panel need opposite answers
    Settings text size (uiSize) server, all screens This screen (calvin-ui-size) A phone and a 7" panel need opposite answers

    On first load after the change, a browser with no local value starts from the old server value, so nothing visibly changes on upgrade. The server key is then only that seed. Everything else stays server-wide.

    Recommendation: yes. Without it, the copy in §3 has to keep warning "applies to every screen", which is the problem we're fixing.

    4. Advanced disclosure¶

    System gets one CollapsibleSection Advanced, closed by default, last in the category. It holds: Repository, Branch, Console logging, Log level, Check for setting changes every. Search (settingsRegistry.js) still finds them and opens the section. No other category gets one: hiding more would make search the only way in.

    5. Copy rules (for every future row)¶

    1. Label = what you'd say out loud: a noun ("Font") or a short verb phrase ("Shuffle photos"). No "Enable".
    2. Description only when the label isn't enough. One sentence, ≤ 110 characters, no "this device" (that's the chip). No "Controls whether …".
    3. Units go on the control ("30 s", "5 min"), never in the label "(s)" or the description.
    4. Never describe the code: no "statusbar", "origins", "polling", "backend", "OS output".
    5. Use the same word for the same thing everywhere: screen (not display), clock bar, plugin, web page.
    6. Options are short, parallel words; "Always on" is "Always" when the label already says what's on.

    This section is the reference until there is a design README.

    6. Tests (vitest)¶

    • Snapshot-free text checks: each renamed label and description in §3 renders verbatim (one test per category file, table-driven).
    • Photo frame: description says idle; the slider default is 5 min when the config value is missing.
    • Theme mode: "On a schedule" shows the Dark from time pickers; each picker writes a whole hour (0–23) to the existing keys.
    • Turn off when idle: "Never" writes displayTimeoutEnabled: false; any other option writes true plus displayTimeout in seconds. An existing value not in the list shows as its own option ("{n} min").
    • The corner rows show only while Hide controls is on.
    • Advanced: closed by default; a search hit for "branch" opens it and scrolls to the row.
    • Kiosks: inherited rows read "Same as all screens"; Use the shared setting removes the override key.
    • §2, if approved: Touchscreen and Settings text size read/write localStorage, seed once from the server value, survive a storage exception (fall back to the server value), and show the This screen chip.
