# WPE WebKit + cog as the Pi 3 kiosk browser

**Research date:** 2026-10-29
**Bead:** `calvin-8by7` (test matrix; not closed by this document)
**Scope:** desk research plus an on-host WebKit compatibility run. No product
code, scripts, units or services were changed. Nothing was installed on, or
measured against, a real Raspberry Pi.

**Status (2026-10-31): implemented as the kiosk default on Pi 3-class boards.**
`auto` in the kiosk installer now resolves to `cog` on the VC4 / Pi 3 family
(Pi 3, 3B, 3B+, 3A+, Zero 2 W, Compute Module 3) and to `x11` on every other
board; an explicit `--display-stack x11|wayland|cog` always wins, and a re-run
keeps an existing kiosk's recorded stack. Owner-approved after on-hardware
verification on a Pi 3B+ (install, rotation via the display agent, screen
off/on, reboot, 24 h soak). The A/B numbers in §5 are still unmeasured, and the
caveats below (native `<select>`, WPE security horizon, no runtime rotation API)
still apply.

## Recommendation

**Superseded 2026-10-31 by the status above.** This section records the original
2026-10-29 conclusion and the evidence it rested on; the Pi 3-class adoption
decision was taken later after hardware verification. **Do not replace Chromium
on the Pi 3B+ yet. Run the A/B in §5 first, and keep Chromium as the default
until it produces numbers.**

The case for cog is real and better than for any compositor swap: one
`apt install` on Trixie Lite gives a DRM/KMS browser with **no X, no Wayland
compositor, and no Chromium GPU stack** — exactly the three layers that are
either heavy or broken on the Pi 3 today (`calvin-scuh`: Chromium 156 must run
with `--disable-gpu` because its GPU path crashes the VC4 renderer). WPE's own
hardware table lists **Raspberry Pi 3 / VideoCore IV / Mesa vc4 / cog `drm` and
`wl`** as a validated configuration, Debian trixie ships everything you need,
and Calvin's frontend boots, renders, opens Settings, registers its service
worker and types through the on-screen keyboard in a WebKit engine with **zero
console errors** (§4).

What holds it back is not compatibility, it is evidence:

1. **No memory win is proven, and there is a warning sign.** Nobody has
   published a Pi 3-class cog memory figure. The only number this research
   produced (§4.5) is from x86_64 and shows **WebKit *above* Chromium** for the
   same page (981 MB vs 536 MB summed RSS). Different engine build, different
   architecture — but it is enough to say "cog is lighter" is an assumption,
   not a fact.
2. **Calvin loses two runtime controls.** Under cog-DRM there is no
   `xrandr`/`wlr-randr` and no `wlopm`: rotation is fixed at cog start
   (`renderer=gles,rotation=N`, needs a restart to change) and panel power has
   no supported path (test `vcgencmd display_power`; otherwise CEC or the
   monitor's own schedule). Today's display agent assumes one of those tools.
3. **A real UI gap upstream:** native `<select>` dropdowns do not open under
   cog's DRM backend (upstream issues #793 and #503, both open). Calvin uses
   `<select>` in plugin config, the calendar-source form and the update tab
   (§4.3). The kiosk can still be configured from a phone ("Use your phone"),
   but Settings-on-the-panel is degraded.
4. **Maintenance:** Debian trixie's `wpewebkit` is 2.48.3, and Debian's
   security tracker currently lists many WebKit CVEs for trixie as
   *vulnerable (no DSA, ignored)*, while Raspberry Pi ships a current Chromium.
   Upstream calls cog a legacy launcher (pre-2.54 API) that new projects should
   replace with a small WPEPlatform launcher.

**The decision rule:** adopt cog for Pi 3B+ SPLIT only if the §5 A/B shows
**≥150 MB lower steady-state memory after one hour**, **first paint no worse
than Chromium's baseline**, and **24 h without an unplanned restart** — and if
we accept that orientation/panel-power become a restart/`vcgencmd`/CEC story or
we move that kiosk to the labwc variant (`cog -P wl` under labwc keeps
`wlopm`). Otherwise stay on Chromium and revisit when Debian 14 ships WPE 2.54
with the built-in DRM platform.

For Pi 4/5 this question is much less interesting: they can afford Chromium and
a compositor, and the Wayland research
([2026-10-29-kiosk-wayland.md](2026-10-29-kiosk-wayland.md)) already covers
them.

| `cog` | **0.18.4-1+b1** (source 0.18.4-1) | launcher; ships `cog`, `cogctl` and the platform modules |
| `libwpewebkit-2.0-1` | **2.48.3-1** | the WPE WebKit engine (shared library + web/network processes) |
| `libwpe-1.0-1` | **1.16.2-1** | legacy embedding library |
| `libwpebackend-fdo-1.0-1` | **1.16.0-1** | legacy FreeDesktop backend (EGL/GBM buffer export) |
| `wpewebkit-driver` | **2.48.3-1** (arch `all`) | WebDriver, for automated testing |

Versions from Debian [madison](https://api.ftp-master.debian.org/madison?package=cog&table=all)
and [packages.debian.org/trixie/cog](https://packages.debian.org/trixie/cog)
(checked 2026-10-29).

**The DRM/KMS platform plugin is included.** The arm64 file list is:

```
/usr/bin/cog
/usr/bin/cogctl
/usr/lib/aarch64-linux-gnu/cog/modules/libcogplatform-drm.so
/usr/lib/aarch64-linux-gnu/cog/modules/libcogplatform-headless.so
/usr/lib/aarch64-linux-gnu/cog/modules/libcogplatform-wl.so
/usr/lib/aarch64-linux-gnu/libcogcore.so.9.2.7
```

([file list](https://packages.debian.org/trixie/arm64/cog/filelist)). That is
cog's default build set (`drm`, `headless`, `wayland`). There is **no X11
platform module**, so "cog inside the current X11/openbox kiosk" is not an
option with Debian's package — cog would need to run on DRM or under Wayland.

Debian's build of the engine is `-DPORT=WPE` with the Bubblewrap sandbox on
(`ENABLE_BUBBLEWRAP_SANDBOX=ON`) and Skia left at its default per
[wpewebkit 2.48.3-1 debian/rules](https://sources.debian.org/src/wpewebkit/2.48.3-1/debian/rules/).
`cog` itself has only `Depends:` (no Recommends), so nothing pulls GStreamer
plugins or fonts for you.

### 1.2 What is in the Raspberry Pi archive

**Nothing.** `http://archive.raspberrypi.com/debian/dists/trixie/main/binary-arm64/Packages.gz`
(1,477 binary packages, fetched 2026-10-29) contains **no `cog`, `wpewebkit`,
`libwpe` or `libwpewebkit` package**. The only WPE-named packages are
`gstreamer1.0-wpe` and its `-dbgsym`, which are GStreamer's WPE sink/source
plugin, not a browser engine — do not confuse the two.

So on Raspberry Pi OS Trixie the packages come from **Debian's** trixie/arm64
archive (Debian 13 is what Pi OS Trixie is built on), and Raspberry Pi does not
test or patch them. Practical consequence: **the Pi gets Debian's 2.48.3, not
the Raspberry Pi-patched Chromium it gets today**, including Debian's security
posture (§1.3) and Debian's feature set.

### 1.3 Version and security horizon

- `cog` 0.18.4 is upstream's May 2024 release; trixie's `cog` saw one binary
  rebuild (`+b1`) and nothing else. Debian 14 (forky) and sid carry 0.18.5 with
  WPE 2.54 — i.e. **cog stays at 0.18.x for trixie's whole life**.
- WPE 2.48's last upstream point release is 2.48.6; trixie has 2.48.3, so any
  later security fixes have to come from Debian.
- Debian's [security tracker for wpewebkit](https://security-tracker.debian.org/tracker/source-package/wpewebkit)
  shows, for trixie, a large number of WebKit CVEs marked
  **`vulnerable (no DSA, ignored)`** at the time of checking (forky/sid show
  `fixed`). That is not a bug in our plan, it is a property of the package; it
  is the strongest non-technical argument for keeping Chromium, which Raspberry
  Pi rebuilds regularly.
- Upstream [WPE FAQ](https://wpewebkit.org/about/faq.html) calls cog the
  *legacy* launcher: "kept for existing deployments, but new projects do not
  need it". Since 2.54 the DRM/Wayland/headless platforms live inside WPE
  WebKit itself (`WPE_PLATFORM=drm`) and a launcher is ~30 lines of C. A future
  Pi OS (Debian 14) migration will be a small custom launcher, not cog.

## 2. Platforms: DRM/KMS vs Wayland

### 2.1 DRM/KMS, no compositor (the interesting variant)

**Yes, and it is a supported configuration.** WPE's
[supported-hardware table](https://wpewebkit.org/about/supported-hardware.html)
lists exactly our target:

> Raspberry Pi 3 · VideoCore IV · Mesa vc4 · backend `fdo` · Cog platforms
> `wl, drm, headless`

The [DRM platform docs](https://github.com/Igalia/cog/blob/0.18.4/docs/platform-drm.md)
add the requirements (WPEBackend-fdo, Wayland **client** libs, GLESv2, libdrm,
libgbm, libinput, libudev — all pulled in by the package) and the knobs:

| Need | How |
|---|---|
| Select the platform | `cog --platform=drm` (or `COG_PLATFORM_NAME=drm`) |
| Resolution / refresh | `COG_PLATFORM_DRM_VIDEO_MODE=1920x1080`, `COG_PLATFORM_DRM_MODE_MAX=1920x1080@60`; default = preferred mode of the first connected output |
| Fullscreen | inherent — there is no window, just a CRTC |
| Rotation | **only** with `--platform-params=renderer=gles,rotation=1` (1 = 90° CCW, 3 = 270°). The default `renderer=modeset` attaches frames directly and **cannot rotate** |
| Cursor | **hidden by default**; `COG_PLATFORM_DRM_CURSOR=1` draws a hardware cursor sprite (and implies pointer events) |
| Pointer | off by default; `COG_PLATFORM_DRM_POINTER=1` forwards motion/buttons/scroll |
| Touch + keyboard | always forwarded (libinput), independent of the pointer options |

Operational requirements that are easy to miss:

- **DRM master + input access.** cog opens the KMS device and calls
  `drmModeSetCrtc` (`platform/drm/cog-drm-modeset-renderer.c`), so it needs to
  be DRM master; and libinput needs to read `/dev/input/event*`. On Pi OS Lite
  the reliable recipe is running the unit as **root**; the alternative (user in
  `video` + `input` groups) depends on no other master existing and on udev
  `/dev/input` permissions — **UNVERIFIED on this image**, check with
  `ls -l /dev/dri/card0 /dev/input/event*` and `id`.
- **The seat is hard-coded to `seat0`** in 0.18.4
  (`libinput_udev_assign_seat(..., "seat0")`, `platform/drm/cog-platform-drm.c:1259`).
  Fine on a Pi; would break on a multi-seat setup.
- **The kernel console is on the same CRTC.** Stop `getty@tty1` in the unit
  (`Conflicts=getty@tty1.service`) so boot messages and the getty do not flash
  over/under the page.
- **Rotation and touch.** 0.18.1 fixed touch-region dimensions for 90°/270°
  ([NEWS](https://github.com/Igalia/cog/blob/0.18.4/NEWS)) and 0.18.4 tries to
  set libinput's per-device rotation to match
  (`libinput_device_config_rotation_set_angle`, `cog-platform-drm.c:1019`).
  Many touch drivers do not support device rotation, in which case the call is
  skipped; finger positions then have to be checked on the actual panel. On the
  Pi 3 that means: **test all four orientations with a tap target, not just the
  picture.**
- **Rotation is a startup property.** It can be changed at runtime through the
  `CogDrmPlatform:rotation` GObject property, but cog exposes no D-Bus action
  for it, so in practice changing orientation = rewrite the unit's
  `platform-params` and `systemctl restart`. (Calvin's display agent currently
  rotates with `xrandr`/`wlr-randr` at runtime.)
- **Known upstream DRM bugs in this release line:** #748 (0.18.4 + DRM + GLES:
  "Cannot create framebuffer (Bad file descriptor)", fd exhaustion after a few
  seconds), #794 (open PR: DRM cold start / SHM robustness / cursor fixes for
  compositor-less boots, i.e. released 0.18 is known to be fragile exactly on
  "boot straight into cog"). Neither is confirmed on VC4, but both are the same
  shape of failure we must watch for in the first ten boots.

### 2.2 Wayland (labwc)

Also supported (`-P wl`, module present). Requirements from the
[wl platform docs](https://github.com/Igalia/cog/blob/0.18.4/docs/platform-wl.md):

- compositor running first, with `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR` in the
  service environment, and access to `/dev/dri` (render node is enough here);
- `COG_PLATFORM_WL_VIEW_FULLSCREEN=1` for a real fullscreen surface (it is a
  *request*; labwc honours it);
- F11 toggles fullscreen — with a USB keyboard attached that can un-fullscreen
  the kiosk. On a touch-only wall there is no way to press it.
- input, touch and cursor belong to labwc. **Cursor hiding is the same problem
  as Chromium today** (one-shot `HideCursor` + `WarpCursor`, reappears on
  touch), i.e. worse than cog-DRM, which never draws one.
- rotation is the compositor's job (`wlr-randr --transform`), so the existing
  agent code path and **`wlopm` panel power keep working**. That is the main
  reason to prefer this variant if the panel-power schedule matters.
- cog's own D-Bus control is on the **session** bus by default
  (`cog_dbus_control=user`, upstream default; Debian does not flip it, and the
  package ships no system-bus policy), so `cogctl` only works when cog runs
  inside a user session with a session bus — under labwc, if `dbus-user-session`
  is installed. **UNVERIFIED on Pi OS Lite**; do not build a watchdog on it.

### 2.3 Which needs what — summary

| | DRM/KMS (`-P drm`) | Wayland (`-P wl`, labwc) |
|---|---|---|
| Compositor | none | labwc (existing `calvin-wayland.service`) |
| Extra packages | `cog` only | `cog` + labwc stack (already used by the opt-in Wayland install) |
| Permissions | DRM master + `/dev/input` (root on Lite) | `/dev/dri` render node; input via compositor |
| Seat | libinput `seat0`, hard-coded | compositor's |
| Fullscreen | inherent | `COG_PLATFORM_WL_VIEW_FULLSCREEN=1` |
| Cursor | never drawn (unless enabled) | compositor cursor; needs the labwc hide hack |
| Touch | libinput → page; rotation via libinput device rotation (driver-dependent) | wlroots maps touch to output and follows the transform |
| Rotation | start-up only, `renderer=gles` only | runtime, `wlr-randr`, follows compositor |
| Panel power | no supported path (test `vcgencmd`, CEC) | `wlopm` (existing agent path) |
| Escape hatch used by today's agent | none | none (agent is xrandr/wlopm-based, still works) |

## 3. Kiosk needs

| Need | cog behaviour | Verdict for Calvin |
|---|---|---|
| **Fullscreen** | DRM: yes by construction. Wayland: `COG_PLATFORM_WL_VIEW_FULLSCREEN=1`. | Good. F11 un-fullscreens on Wayland with a keyboard. |
| **Fixed URL** | URL argument or `COG_URL`; no address bar, tabs, or navigation UI. The URL can only be changed at runtime through the session-bus `cogctl open` (or by restarting). | Good; also simpler than Chromium's kiosk flags. |
| **Auto-restart on a crashed page** | `--webprocess-failure=restart`: retries the web process **up to 5 times inside a 1 s window**, then renders cog's built-in "Crash!" / "Out of memory!" page (`launcher/cog-launcher.c:350`, `core/cog-webkit-utils.c`). Default is `error-page`; `exit`/`exit-ok` also exist. | Good **with a watchdog**: the fallback error page has no reload path, so a hung/crashed renderer can sit there forever. Run the unit with `Restart=always` and add an HTTP health watchdog. |
| **Cursor hiding** | DRM: no cursor at all unless `COG_PLATFORM_DRM_CURSOR` is set. Wayland: compositor cursor. | DRM is better than anything we have today. |
| **Autoplay video** | WPE 2.48's `WebKitSettings:media-playback-requires-user-gesture` default is *off* ("media playback could start automatically", [WebKitSettings.cpp, 2.48 branch](https://github.com/WebKit/WebKit/blob/webkitglib/2.48/Source/WebKit/UIProcess/API/glib/WebKitSettings.cpp)). It can be pinned with `[websettings]` in a `--config` file. Audible-audio policy is a separate WebKit preference; **UNVERIFIED** whether unmuted video autoplays. | Probably fine for muted loops; test the actual plugin. **Install GStreamer plugins** (`gstreamer1.0-plugins-good/bad/libav`) — Pi OS Lite has none, and cog's package does not recommend them. VC4 gives no hardware H.264 to GStreamer anyway, so expect software decode. |
| **Crash reporting** | Everything goes to stderr → journal: platform init, web-process termination reason (`CRASHED` / `EXCEEDED_MEMORY_LIMIT`), retry attempts, then the error page. No metrics, no HTTP status. `WEBKIT_INSPECTOR_SERVER=0.0.0.0:2999` exposes the remote Web Inspector for live console/network checks. | Adequate if we add a systemd watchdog (cogctl is not reachable from a system unit; use the backend's `/api/health`). |
| **Memory on Pi 3-class hardware** | **No published measurement found.** What exists: cog issue #65 (2018, Snapdragon 410) shows the three-process model — `cog` + `WPEWebProcess` + `WPENetworkProcess` — and a ~25 MB/hour leak in a canvas page; that issue is still open and is not evidence about 2.48. WPE marketing says "small footprint" but gives no number. §4.5 has this host's measurement and the reason it is not a Pi answer. | **Unknown — this is the go/no-go gate.** Measure in §5. |

Chromium today uses ~600 MB of the Pi's 905 MB (given). If cog lands under
~450 MB steady-state, the A/B is a win worth taking; if it lands at 600 MB too,
cog buys nothing but risk.

## 4. Calvin frontend compatibility

### 4.1 Method

Built the real frontend and drove it in a WebKit engine on this machine:

```bash
cd frontend
npm ci
npm run build                     # dist/, 2.06 s, no errors
```

Engine: **Playwright 1.59.1's WebKit**, which on Linux is the **WPE MiniBrowser**
(`webkit-2272`, `navigator.userAgent … Version/26.4 Safari/605.1.15`) — i.e. the
same engine family as cog, one architecture away and **many versions newer than
Debian trixie's 2.48.3**. It was launched from NixOS' Playwright browser bundle
(`PLAYWRIGHT_BROWSERS_PATH=/nix/store/…-playwright-browsers`, via
`playwright-core` 1.59.1), so no `playwright install`/FHS download was needed.

Serving: a local static server on `127.0.0.1:8731` for `frontend/dist` (not
8000/5173). **No backend was started.** Every `/api/**` answer is a stub:
pass A used `page.route` with service workers blocked; pass B enabled the
service worker and served the same stub JSON from the local server (a service
worker's own fetches bypass `page.route`). Stubs included `/api/config`
(`onScreenKeyboard: "on"`), `/api/auth/status` (authenticated), empty
`/api/plugins`, `/api/calendar/*`, `/api/images/list`, `/api/kiosks`,
`/api/keyboard/mappings`.

A Chromium run through the identical harness was used as the control.

### 4.3 WebKit-specific issues found

**A. Native `<select>` dropdowns do not open under cog's DRM backend.**
Upstream, open: [cog #793](https://github.com/Igalia/cog/issues/793) ("cog with
DRM backend doesn't support dropdowns", 0.18.5/2.50, reported on a Pi-class
board) and [cog #503](https://github.com/Igalia/cog/issues/503) ("Popup menu not
opened when selecting HTML select element"). Calvin uses native selects in:

- `frontend/src/components/PluginFieldRenderer.vue:50` and `:64` — plugin
  `select` config fields (any plugin with a choice field),
- `frontend/src/components/settings/tabs/content/CalendarSourcesTab.vue:15` —
  calendar source type,
- `frontend/src/components/settings/tabs/system/UpdatesTab.vue:30` — update
  branch.

Not visible in the Playwright run (that engine renders popups); it is a
known cog-DRM limitation. On a cog kiosk, those three settings would have to be
changed from a phone/desktop (Calvin already offers "Use your phone" with a QR
code) unless we replace native selects with an in-DOM picker.

**B. Touch auto-detection may not fire under cog.** The on-screen keyboard's
`auto` mode depends on `(any-pointer: coarse)` or
`navigator.maxTouchPoints > 0` (`frontend/src/composables/useTouchCapability.js:32-45`,
and the same signals gate `useOnScreenKeyboard`). In this headless WPE run
`maxTouchPoints` was **0** and `any-pointer: coarse` did not match even with
`hasTouch: true`; the OSK only appeared because the stub config sets
`onScreenKeyboard: "on"`. cog's DRM platform forwards libinput touch events but
what WPE reports to the page is **UNVERIFIED**. **Mitigation:** set
`touchControls: "on"` and `onScreenKeyboard: "on"` (per-kiosk overrides exist)
for any cog kiosk before trusting touch chrome.

**C. `ResizeObserver loop completed with undelivered notifications.`** is
raised as a page *error* in WebKit (Chromium suppresses it). It appeared on
both passes and only on Settings. Candidates:
`frontend/src/components/settings/shell/CategoryRail.vue:51-52` (measure on
observe; the rail's contents change when a category is selected),
`frontend/src/components/ui/OnScreenKeyboard.vue:135-136` (height measurement),
and `frontend/src/composables/useFitClamp.js:90`. It is benign — layout settles
and the screenshots are correct — but it is the one non-clean console signal,
and on a Pi it would also fire. No action needed unless it ever loops.

**D. Service worker + `page.route` interaction (harness, not product).** An
early run produced `SyntaxError: The string did not match the expected pattern`
on `/api/keyboard/mappings` and `/api/auth/status`. Cause: the page registered
its service worker, and Playwright routing does not intercept fetches made by a
service worker, so the worker's network-first fallback got `index.html` from the
static server and WebKit's `JSON.parse` produced that message. Not a WebKit bug
and not a cog issue; but it is a useful reminder for anyone testing Calvin with
Playwright WebKit: **block service workers, or serve API stubs from the server,
not only from `page.route`.**

**E. No other engine-specific problems.** Dialogs, the QR code (canvas),
the clock bar, the calendar grid, the photo pane, `backdrop-filter` surfaces,
the settings search, the keyboard's `inert`/`aria-hidden` handling and
`Teleport` to `body` all rendered correctly.

**F. Not exercised (no backend, by design):** SSE (only used for the update log
stream, `frontend/src/composables/useSystem.js:210`), plugin iframes, full-size
photo decoding, video playback, admin sign-in round-trip, and anything that
touches `/api/system/*` (stubbed out and never called on a live backend).

### 4.4 What this run does and does not prove

- Proves: the built frontend is engine-portable to WebKit's layout/JS stack; the
  OSK, router, Pinia stores, service worker and CSS feature set all work without
  a Chromium-only API.
- Does **not** prove: behaviour on WPE **2.48.3** (⅓ of the version gap in the
  other direction), VC4 GLES paths, cog's popup handling, libinput touch
  semantics, JIT/heap behaviour on Cortex-A53, or memory on 1 GB.

### 4.5 Memory, measured — and why it is not a Pi number

Same built page, same 1280×800 viewport, same stubs, this host (x86_64,
NixOS), 12 s after load, summing all browser processes:

| Engine | Sum RSS | Sum PSS | Notes |
|---|---|---|---|
| WPE MiniBrowser (WebKit **26.4**, Skia, headless) | **981 MB** | **696 MB** | 4 processes; one web/content process at 679 MB RSS / 585 MB PSS |
| Chromium (headless shell, same page) | **536 MB** | **281 MB** | 11 processes |

Blank-page control: WPE 489 MB RSS, Chromium 378 MB. So the engine baseline is
already heavier here, and the dashboard adds more.

**Do not read this as "cog will use 1 GB on a Pi".** It is a different build of
a newer engine on a different architecture with different raster settings, and
PSS on x86 shares a lot of mapped library pages. What it does establish is the
absence of any evidence that WPE is automatically the leaner engine — which is
why the Pi measurement in §5 is the actual decision, not this table.

## 5. On-Pi test plan (coordinator, over SSH)

Preconditions: Pi 3B+ on Raspberry Pi OS **Trixie Lite 64-bit**, SPLIT topology,
working Chromium kiosk, SSH access, panel attached, and a way to see the screen
(photo is fine). Run as the kiosk user with sudo. Nothing here calls
`/api/system/*`; the horizontal checks use `curl /api/health` only.

### 5.1 Baseline first (Chromium, current stack)

```bash
# what is running now
systemctl list-units 'calvin-*' --no-pager
free -m; vcgencmd measure_temp; vcgencmd get_throttled
# memory of the current stack, 10 samples over 5 min
for i in $(seq 10); do
  printf '%s ' "$(date -Is)"
  free -m | awk 'NR==2{printf "used=%sMB avail=%sMB ", $3, $7}'
  ps -eo rss=,comm= | awk '/chromium/{s+=$1} END{printf "chromium_rss=%dMB\n", s/1024}'
  sleep 30
done | tee ~/baseline-chromium.log
```

Also note "cold boot to dashboard" three times (`systemd-analyze` plus a
stopwatch on the panel) and `curl -s -o /dev/null -w '%{time_starttransfer}\n'
https://calvin.example.com/api/health` for the network baseline.

### 5.2 Install cog (Chromium untouched)

```bash
sudo apt update
apt-cache policy cog libwpewebkit-2.0-1
sudo apt-get -s install --no-install-recommends cog | tail -5   # size preview
sudo apt install --no-install-recommends cog
# only if a plugin plays video; Pi OS Lite ships no GStreamer plugins
sudo apt install gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-libav
cog --version                       # expect: cog 0.18.4 (WPE WebKit 2.48.3)
ls /usr/lib/*/cog/modules/          # expect: libcogplatform-{drm,headless,wl}.so
```

### 5.3 First run by hand (DRM, no unit yet)

```bash
sudo systemctl stop calvin-x.service calvin-kiosk-remote.service calvin-display-agent.service
sudo systemctl stop getty@tty1.service
sudo cog --platform=drm \
     --platform-params=renderer=modeset \
     --webprocess-failure=restart \
     'https://calvin.example.com/'
```

Watch the console for the first 2 minutes. Success = dashboard in <15 s, no
`Cannot create framebuffer`, no repeated `Renderer process terminated`. Then
`Ctrl+C` and repeat from a cold boot once you have the unit.

### 5.4 Variant A — DRM/KMS unit

`/etc/systemd/system/calvin-cog.service`:

```ini
[Unit]
Description=Calvin kiosk (cog + WPE WebKit, DRM/KMS)
Wants=network-online.target
After=network-online.target systemd-udev-settle.service
Conflicts=getty@tty1.service

[Service]
Type=simple
# Root gives DRM master and /dev/input access on a Lite image.
# Alternative: User=calvin, SupplementaryGroups=video input, with no other DRM master.
Environment=COG_PLATFORM_DRM_VIDEO_MODE=1920x1080
Environment=COG_PLATFORM_DRM_MODE_MAX=1920x1080@60
ExecStart=/usr/bin/cog --platform=drm --platform-params=renderer=modeset \
          --webprocess-failure=restart https://calvin.example.com/
Restart=always
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=graphical.target
```

Portrait/180°: replace `renderer=modeset` with
`renderer=gles,rotation=1` (90° CCW) or `rotation=3` (270°), or `rotation=2`
for 180°. Changing orientation needs a unit edit + restart; note that in the
result.

```bash
sudo systemctl daemon-reload
sudo systemctl disable --now calvin-kiosk-remote.service calvin-x.service
sudo systemctl enable --now calvin-cog.service
journalctl -u calvin-cog -f
```

### 5.5 Variant B — cog on labwc (keeps `wlopm`)

Use the existing Wayland install (`--display-stack wayland`, KIOSK_INSTALL.md),
then replace the Chromium line in `~/.config/labwc/autostart` with:

```sh
COG_PLATFORM_WL_VIEW_FULLSCREEN=1 cog 'https://calvin.example.com/'
```

(or a user unit with `Environment=WAYLAND_DISPLAY=wayland-0`,
`XDG_RUNTIME_DIR=/run/user/1000`, `COG_PLATFORM_WL_VIEW_FULLSCREEN=1`).
Rotation stays `wlr-randr`, panel power stays `wlopm` — the existing agent keeps
working.

### 5.6 Measurements

```bash
# memory: PSS of each cog process + system available, every minute for an hour
for i in $(seq 60); do
  printf '%s ' "$(date -Is)"
  for p in $(pgrep -x cog) $(pgrep -f WebKitWebProcess) $(pgrep -f WebKitNetworkProcess); do
    printf '%s=%sMB ' "$(cat /proc/$p/comm)" \
      "$(( $(awk '/^Pss:/{print $2}' /proc/$p/smaps_rollup 2>/dev/null || echo 0) / 1024 ))"
  done
  free -m | awk 'NR==2{printf "used=%sMB avail=%sMB\n", $3, $7}'
  sleep 60
done | tee ~/cog-mem.log

# CPU / temperature / throttling
sudo apt install -y sysstat
pidstat -h -p "$(pgrep -x cog)" 5 12
vmstat 5 12
vcgencmd measure_temp; vcgencmd get_throttled
journalctl -u calvin-cog -p warning --since '-1h' --no-pager

# load time: unit start → first backend request (the server side is the honest clock)
systemd-analyze blame | head
systemd-analyze critical-chain calvin-cog.service
journalctl -u calvin-cog -o short-precise | head -20
# on the Calvin server, at the same moment:
#   docker logs --since 5m calvin 2>&1 | grep -E "GET /api/(config|health)"

# crash drill: kill the renderer and watch recovery
sudo kill -9 "$(pgrep -f WebKitWebProcess | head -1)"
sleep 5; journalctl -u calvin-cog -n 20 --no-pager
```

### 5.7 Panel checks (someone at the screen)

1. Dashboard renders; photos rotate; clock bar is right.
2. Touch: every region, the hot corner, and a swipe/drag.
3. Settings → Display → "Display name": tap the field, type with the on-screen
   keyboard, confirm the field updates and stays focused.
4. Settings → Content Sources → Calendars → "type" dropdown: **expected to fail**
   under cog DRM (issue #793) — record what happens.
5. Rotation: all four orientations, and re-tap the same target after each.
6. Cursor: no arrow at rest, none after a tap.
7. Panel power: `sudo vcgencmd display_power 0` then `1`. If that does nothing
   under KMS, record it — it means the schedule needs CEC or the monitor's own
   timer, or this kiosk should use variant B.
8. Cold boot 10×: no boot text left on screen, no blank frame that stays.

### 5.8 Soak and acceptance

24 h at the dashboard with a 5-minute memory sample (`sleep 300`), plus
`journalctl -u calvin-cog -p warning` and `dmesg | grep -iE 'vc4|drm'` at the
end.

**Adopt cog** if all of these hold:

- steady-state PSS (cog + web + network) **< 450 MB** after 1 h, and at least
  **150 MB below** the Chromium baseline;
- first dashboard paint **no worse than Chromium +10 %**;
- 24 h with **no unplanned restart**, no `Renderer process terminated` storm;
- touch, OSK and rotation verified physically;
- the `<select>` workaround is acceptable (configure from a phone) or a fix is
  scheduled;
- panel power has a working path, or that kiosk's schedule is disabled;
- rollback (§5.9) tested once.

**Reject / keep Chromium** on any failed gate, or if memory comes out within
noise of Chromium — in that case cog costs a second engine, a stale CVE set and
a lost display-control path for nothing.

### 5.9 Rollback

```bash
sudo systemctl disable --now calvin-cog.service
sudo systemctl enable --now getty@tty1.service
# X11 stack
sudo systemctl enable --now calvin-x.service calvin-kiosk-remote.service calvin-display-agent.service
# or the Wayland stack, if that is what the kiosk had
# sudo systemctl enable --now calvin-wayland.service
```

Chromium and the X11/labwc packages were never removed, so this is a service
switch, not a reflash. `sudo apt remove cog` is optional and only frees space.

## 6. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| cog uses as much RAM as Chromium (or more) | Medium | No reason to switch | Measure first (§5); accept/reject on the number |
| DRM+GLES hits a VC4 bug similar to Chromium's | Low–medium | Black screen / framebuffer errors | Variant B (Wayland) as fallback; journal the first boot; issue #748 is the signature to watch for |
| Touch unreliable (upstream #737/#456) | Medium | Kiosk unusable by finger | Variant A/B test on the real panel; fall back to Chromium |
| Rotation needs restart; touch mapping wrong after rotation | Medium | Portrait kiosk wrong | `renderer=gles,rotation=N`; physical tap test in all four orientations |
| No panel-power path under DRM | High | Night schedule stops working | `vcgencmd` test; CEC; monitor timer; or variant B with `wlopm` |
| `<select>` dropdowns dead on the kiosk | High (DRM) | Settings degraded | Configure from phone; or replace native selects |
| Trixie's wpewebkit gets no security updates (tracker: "vulnerable, ignored") | High | Long-lived unpatched browser | Keep Chromium as default; if adopted, restrict the kiosk's network reach and re-check the tracker each Pi OS point release |
| cog 0.18 is legacy; Debian 14 moves to WPE 2.54 | Certain eventually | Launcher rewrite | Treat cog as a stop-gap; plan a ~30-line WPEPlatform launcher at the next OS cycle |
| Second browser engine on the image (+deps) | Certain | Disk/SD wear, update surface | `--no-install-recommends`, remove cog if rejected |

## 7. Open questions / explicitly UNVERIFIED

- **UNVERIFIED:** cog's memory on a Pi 3B+ (the whole point of §5).
- **UNVERIFIED:** whether WPE 2.48.3 in Debian behaves like the 26.4 engine used
  in §4 for CSS features, service workers and the OSK (near-certain, not proven).
- **UNVERIFIED:** whether cog's DRM platform reports touch capability to the
  page such that `(any-pointer: coarse)` / `maxTouchPoints` become non-zero.
  Assume not; force `touchControls`/`onScreenKeyboard` to `on`.
- **UNVERIFIED:** audible autoplay; the WebKit default allows media playback
  without a gesture, but audio has a separate policy.
- **UNVERIFIED:** whether `vcgencmd display_power` still controls HDMI once cog
  owns the KMS CRTC on a Pi 3.
- **UNVERIFIED:** whether Pi OS Lite's PAM/logind session provides a session bus
  for `cogctl` under `calvin-wayland.service`.
- **UNVERIFIED:** the exact installed/download size of `cog` + `libwpewebkit`
  (use `apt-get -s install cog`).
- **UNVERIFIED:** whether `cog` survives a 24 h VC4 soak; no public report found
  either way, on any Pi model.
