# A Calvin app for Homey

**Date:** 2026-11-19
**Scope:** a Homey Pro app that shows Calvin's screens as Homey devices, and what Calvin would add for it
(`backend/app/security/`, `backend/app/api/routes/{kiosks,auth}.py`, `backend/app/services/kiosk_registry.py`).
Builds on [Screen power from home automation, and scoped API keys](2026-11-18-screen-power-and-scoped-keys.md)
and [Home automation: turn screens on and off](../integrations/HOME_AUTOMATION.md). Research only: no product
code changed, and no Homey, Calvin server or household device was contacted. Outside facts come from Athom's
public developer docs ([Homey Apps SDK](https://apps.developer.homey.app/), full text at
<https://apps.developer.homey.app/llms-full.txt>); "not documented" marks what those docs do not say.

## Recommendation

Build a **Homey Pro only** app (`"platforms": ["local"]`, SDK v3, TypeScript on Node.js) in a **new public repo,
`calvin-homey`**, and install it with `homey app install` first. One driver, *Calvin screen*: each Calvin screen
is a Homey device with the standard **`onoff`** capability (on or off means "hold on" or "hold off", read back
from Calvin's `desiredOn`), a read-only custom capability **"Held by Homey"**, an offline alarm, and one extra
action card, **"Return to its schedule"**. The connection (Calvin address and a `screens.power` key) is entered
once, during the first pairing, and kept in the app's own settings, never in a flow card. The app **polls**
Calvin every 30 seconds; Homey's built-in `onoff` and custom-capability triggers then give "screen turned
on/off" and "screen held / no longer held" for free. **The first version needs nothing new in Calvin**: the
screen list and each screen's state are already public reads, and the existing key opens the one write
(`route_policy.py:95-104`). Three Calvin additions come later, in this order, and only the first two are
needed before an App Store release: an **mDNS advertisement** (Athom rejects store apps that make users type an
address when discovery could work), a **pairing code** in Settings so nobody copies a key by hand, and an
**event stream** so triggers fire within a second instead of 30. Homey Cloud is out: a Homey Bridge cannot
reach a LAN server, and cloud apps need a paid Verified Developer account that only businesses can get. Keep
the calvin-plugins `homey` plugin as it is. Rough size: the first app version is 3 to 5 days, plus 1 to 2 days of
the owner's time on a real Homey; the three Calvin additions are about 4 to 6 days together.

## 1. What a Homey app can be

**Structure.** An app is a folder with a generated `app.json` manifest (built by *Homey Compose* from
`.homeycompose/` and `*.compose.json` files; never edited by hand), an `App` class (`app.js`/`app.mts`) that runs
once, `drivers/<id>/` with a `Driver` and a `Device` class per device type, flow cards under
`.homeycompose/flow/`, optional `settings/index.html` (app settings page), optional `api.js` (the app's own Web
API), `locales/`, and `assets/` with icons and images
([App](https://apps.developer.homey.app/the-basics/app),
[Manifest](https://apps.developer.homey.app/the-basics/app/manifest),
[Homey Compose](https://apps.developer.homey.app/advanced/homey-compose)).

- **Devices and capabilities.** A device's state is a set of capabilities. System ones (`onoff`, `dim`, …) come
  with UI, flow cards and voice assistant support; an app may define **custom capabilities** of type boolean,
  number, enum or string, with `getable`/`setable` and a `uiComponent` (toggle, sensor, picker, button, or none)
  ([Capabilities](https://apps.developer.homey.app/the-basics/devices/capabilities)). A device can be marked
  unavailable, which blocks its capabilities and flow actions
  ([Drivers & Devices, Availability](https://apps.developer.homey.app/the-basics/devices#availability)).
  Device class `other` is the documented fallback when no class fits
  ([Device class](https://apps.developer.homey.app/the-basics/devices#device-class); the class reference page is
  script-rendered and did not show whether a `tv` or display class exists, so check it in the CLI's
  `homey app driver create`).
- **Flow cards.** Triggers ("when"), conditions ("and") and actions ("then"), defined in the manifest. Device
  cards take the device as an argument, so one card serves every screen
  ([Flow](https://apps.developer.homey.app/the-basics/flow)). For a custom boolean capability Homey runs the
  triggers `<id>_true` and `<id>_false` by itself when the app sets the value
  ([Flow, custom capability changed](https://apps.developer.homey.app/the-basics/flow#custom-capability-changed)).
- **Settings.** Per device: user-visible *device settings*, and a hidden *device store*. Per app:
  `ManagerSettings` (any JSON value, kept until the app is removed), with an optional custom HTML page on Homey
  Pro only ([Persistent Storage](https://apps.developer.homey.app/the-basics/app/persistent-storage),
  [App Settings](https://apps.developer.homey.app/advanced/custom-views/app-settings)).
- **Pairing.** A driver lists pairing views: system ones (`list_devices`, `add_devices`, `login_credentials`,
  `pincode`, `loading`, `done`) or custom HTML views that talk to the driver through a pairing session. A driver
  can also offer **repair**, to fix credentials without breaking the user's flows
  ([Pairing](https://apps.developer.homey.app/the-basics/devices/pairing),
  [Custom Pairing Views](https://apps.developer.homey.app/advanced/custom-views/custom-pairing-views)).
- **Widgets.** Dashboard widgets need Homey 12.3.0 or newer and do not work on Homey Cloud
  ([Widgets](https://apps.developer.homey.app/the-basics/widgets)). Not for the first version.

**Language.** JavaScript, TypeScript (`.mts`, compiled by `homey app build`) or, newly, **Python** (needs
`"compatibility": ">=13.0.0"` and Python 3.14; Docker is needed to test it)
([App, Python](https://apps.developer.homey.app/the-basics/app#python),
[Getting Started](https://apps.developer.homey.app/the-basics/getting-started)). Python would match Calvin's
backend, but which Homey models get Homey 13 is not documented, and nearly all examples and community apps are
Node. Pick **TypeScript**: it runs on every Homey Pro, and plain-JS packages only (native addons are
discouraged) ([App, Node.js](https://apps.developer.homey.app/the-basics/app#node.js)).

**Homey Pro vs Homey Cloud.** On Homey Cloud the app runs in Athom's data centre for many households at once,
and the household has a Homey Bridge instead of a Pro. The Bridge "does not support local Wi-Fi connections", so
mDNS, SSDP and MAC discovery do not work, an app's own Web API is not allowed, app settings pages are not
allowed, and `connectivity: lan` "is not possible with Homey Bridge"
([Homey Cloud](https://apps.developer.homey.app/guides/homey-cloud)). A cloud app could only reach Calvin if
Calvin were reachable from the internet, which Calvin does not want. Publishing for Cloud also needs the
**Verified Developer** subscription, which is open to "registered business or institution" only, and only
official brand integrations are approved
([Verified Developer](https://apps.developer.homey.app/app-store/verified-developer)). So: **Homey Pro only**.

**Homey Pro versions.** Every Homey Pro runs SDK v3 apps (SDK v3 needs Homey 5.0.0 or newer). From Homey
12.9.0, all of them, the 2016-2019 model, the Early 2023 model and Homey Pro mini, run apps on Node.js 22
([App, Node.js table](https://apps.developer.homey.app/the-basics/app#node.js)). The 2016-2019 model cannot run
an app in a local Docker container during development: `homey app run` uploads it to the Homey instead
([Homey CLI](https://apps.developer.homey.app/the-basics/getting-started/homey-cli)). Set
`"compatibility": ">=12.9.0"` so one Node version is the target; the owner's model and firmware decide whether
that is too strict (question 4).

## 2. What the Calvin app should offer

### Devices

| Option | For | Against |
|---|---|---|
| **A. Each screen is a device** with `onoff` | Native tile, voice assistants, built-in on/off flow cards, Homey's own "turned on/off" triggers and "is on" condition | `onoff` has two values; Calvin has three (on, off, schedule) |
| B. One "Calvin" device with a picker per screen | One device | Not native; flows must name screens in arguments |
| C. Flow cards only, no devices | Smallest | Nothing in the Homey app's device list; the owner asked for devices |

**Pick A.** How the three Calvin states map:

- `onoff` **value** = Calvin's `desiredOn` for that screen (`kiosks.py:215-231`). It follows the schedule when
  nothing is held, so a scheduled change shows up in Homey too. It is the intent, not a measurement of the
  panel, as the existing doc says ([HOME_AUTOMATION.md](../integrations/HOME_AUTOMATION.md)).
- **Setting** `onoff` (tile, voice, flow) sends `PUT .../screen-power` with `on` or `off`, which holds.
- **"Return to its schedule"**: a device action card (sends `schedule`). Also add it as a button capability flagged
  as a *maintenance action*, so it is reachable from the device's settings without a flow
  ([Capabilities, Maintenance Actions](https://apps.developer.homey.app/the-basics/devices/capabilities#maintenance-actions)).
  A three-value enum `power` capability with a picker was considered: it fits Calvin's model exactly, but it
  replaces the native on/off tile and loses voice control. Not in the first version.
- **"Held by Homey"**: a custom read-only boolean capability (`calvin_held`, `setable: false`) from Calvin's
  `held`. Homey then runs `calvin_held_true` / `calvin_held_false` triggers by itself, and a device condition
  card "is held" is a few lines. Strictly, `held` is true for any hold, including one set in Settings by an
  admin (`by: "settings"`); the title should say "Held" and the card hint explain it.
- **Offline**: a custom boolean `alarm_calvin_offline` from Calvin's `online` (last poll under 120 s,
  `kiosks.py:188`). Do **not** use `setUnavailable()` for an offline screen: that blocks flow actions, and a hold
  sent while a screen is offline is still stored and obeyed when it comes back. Mark devices unavailable only
  when Calvin itself cannot be reached or refuses the key.
- **Old screen software**: when `agentHolds` is `false`, show a device warning ("This screen's software is too old
  to hold. Update it in Calvin Settings."), because the hold only lasts until the next scheduled change there.

### Flow cards

| Card | Kind | First version |
|---|---|---|
| Turn on / Turn off / Is on / Turned on / Turned off | Built in with `onoff` | Yes, free |
| Return to its schedule | Action | Yes |
| Is held / Became held / Is no longer held | Condition / triggers | Yes (custom capability) |
| Went offline / Came back online | Triggers | Yes (from the alarm capability) |
| Turn every screen on / off / back to schedule | App action | Yes, small: loops the paired screens |
| A touch on a screen | Trigger | No: Calvin has no touch event outside the browser |
| Show a page / show a message | Action | No: Calvin has no route for it yet; a later design |

Flow card titles must be short, without device names, parentheses or "When/And/Then"
([Guidelines 1.9](https://apps.developer.homey.app/app-store/guidelines)).

### Connection: app level or per device

A household has one Calvin server and several screens. Keep **one connection per Calvin server, in the app's
`ManagerSettings`** (address, key, server id), entered during the first pairing; each screen device keeps only
its `data.id` (the kiosk id, never the address, per Athom's pairing advice) and a store reference to its server.
Later pairings skip straight to the screen list. Per-device settings would repeat the key for every screen and
make a key change touch every device. Use **repair** on any screen to change the address or key for all of
them. A custom app settings page is allowed on Homey Pro, but the guidelines prefer pairing, and the page would
be one more place the key could be shown; leave it out.

## 3. Pairing and discovery

**How a Homey app finds a LAN server.** Through a discovery strategy in the manifest: **mDNS-SD** (a service
name and protocol, with an `id` template such as `{{txt.id}}` and optional conditions on TXT values), SSDP, or a
MAC address prefix. Linked to a driver, Homey also tells each device when the address changes
(`onDiscoveryAddressChanged`) and manages its availability
([Discovery](https://apps.developer.homey.app/wireless/wi-fi/discovery)). Athom's Wi-Fi page warns:
"App Store submissions where users must enter an IP address, where discovery could have been used instead, will
be rejected" ([Wi-Fi](https://apps.developer.homey.app/wireless/wi-fi)).

**What Calvin advertises today: nothing.** No mDNS or SSDP code exists in the backend; only setup docs mention
`.local` names. Calvin would add an mDNS service, for example `_calvin._tcp` on its port, with TXT
`id=<stable server id>`, `v=1` (API generation) and `name=<household name>`. Calvin has no stable server id
yet: generate a random one in `settings.data_dir` on first start. Risky part: inside Docker, mDNS needs host
networking or an avahi service file on the host (see [Deployment topologies](../setup/DEPLOYMENT_TOPOLOGIES.md)),
so the advertisement may be easier as a host-side file written by setup than as Python in the backend. Manual
address entry stays as the fallback, and is enough for the first, CLI-installed version. Calvin's Host check
already accepts an IP, a single-label name or a `.local` name (`host_origin.py:58-90`), and a bearer request
skips the Origin check (`host_origin.py:163-170`), so the app's requests pass as they are.

**How the app gets a key.** Three options:

| Option | How | Calvin work | Fit |
|---|---|---|---|
| **A. Paste a key** | Create a "Turn screens on and off" key in Settings (as today), paste it in a custom pairing view | None | First version |
| **B. Pairing code** | Settings › Screens › "Connect Homey" shows a 6-digit code for 5 minutes; Homey's `pincode` view sends it; Calvin creates a `screens.power` key named after the Homey and returns it once | A new public write route, a short-lived code store, rate limit, a Settings button | App Store version |
| C. OAuth-like redirect | Homey opens Calvin in a browser, the admin approves | Login redirect flow, callback URLs; Homey's OAuth2 view is meant for cloud services | Too much for a LAN app |

**Pick A now, B before the store.** Key creation is admin-only today (`auth.py:409-410`), and the code is the
only safe way to let an unauthenticated device obtain one: one-time, short-lived, rate-limited (reuse the
bearer limiter, `route_policy.py:255-281`), created only while an admin has the dialog open, and logged by key
name. That route sits in `backend/app/security/` and `api/routes/auth.py`, the highest-risk paths, so it needs
its own design and tests.

**Does the app need more than `screens.power`?** Not for the first version. `GET /api/kiosks` (screen ids,
names in `overrides.displayName`, `lastSeen`, `powerHold`, `agentHolds`; `kiosks.py:49-52`,
`kiosk_registry.py:380-410`) and `GET .../screen-power` are public reads; the key only opens the `PUT`
(`route_policy.py:95-104`). A limited key gets no less than an anonymous caller (`route_policy.py:359-378`).
Two small, optional additions would help:

- `GET /api/auth/key`: the calling key's name and permissions, so pairing can say "this key cannot switch
  screens" instead of failing on the first switch. Today a revoked or wrong key already gives `401` on any route
  (`route_policy.py:255-281`), so the app can test "is the key valid" with `GET /api/kiosks`, but it cannot tell a
  `screens.power` key from an admin key. It should warn when given an admin key, and Calvin cannot tell it so.
- `GET /api/kiosks/screen-power`: every screen's state in one answer, so a poll is one request, not one per
  screen. It would go in `PERMISSION_ROUTES` for documentation only, like the per-screen `GET`.

A `screens.read` permission is only needed if Calvin ever closes the screen list to anonymous callers (it hints
at presence; see [HOME_AUTOMATION.md, security notes](../integrations/HOME_AUTOMATION.md#security-notes)). Name
it then, not now.

## 4. State and events

| Way | How | Calvin work | Latency | Verdict |
|---|---|---|---|---|
| **Poll** | The app reads Calvin's screen states every 30 s and after each command | None (one call per screen), or the bulk `GET` | Up to 30 s | First version |
| **Event stream** | The app keeps one HTTP connection open to a Calvin SSE route that sends a line on every hold change and online/offline change | A new SSE route (Calvin already streams one, `system.py:747-749`), events from `set_power_hold` / `clear_power_hold` and the last-seen writer | Under a second | Second step |
| Webhook into Homey | Calvin posts to the app's own Web API on the Homey (`/api/app/<appId>/...`) | Store a Homey address and secret, send with retries, handle a moved Homey | Under a second | No |
| Homey Cloud webhook | Calvin posts to Athom's forwarding service, which reaches the Homey | Calvin talks to the internet; a developer webhook id and secret | Seconds | No |

The app Web API exists on Homey Pro, but its endpoints need a Homey user token unless marked `public: true`, and
Athom says to use public endpoints only "when no alternatives are possible"
([Web API](https://apps.developer.homey.app/advanced/web-api)). A public endpoint means a shared secret that
Calvin must keep and the Homey must check, and Calvin must know the Homey's address. Cloud webhooks go through
Athom's servers ([Webhooks](https://apps.developer.homey.app/cloud/webhooks)), which a LAN-only Calvin should not
need. An event stream is opened by the Homey, so Calvin needs no Homey address and no Homey-side secret, and
it reuses the key the app already has. Whether a Homey app may hold a long-lived connection, and for how long,
is not documented; the app should reconnect and fall back to polling.

**Pick:** poll every 30 s first (a few screens is a few small requests; Calvin's own last-seen writes are 30 s
apart, `kiosk_registry.py:53`), then the event stream. Polls never count toward the 30-changes-a-minute limit,
which applies to changing writes only (`kiosks.py:241-270`, `screen_power.py:168`).

## 5. Distribution

- **Personal use.** `homey login` (Athom account, browser), `homey select`, then `homey app install` builds the
  app and leaves it installed on that Homey ([Homey CLI](https://apps.developer.homey.app/the-basics/getting-started/homey-cli)).
  No store, no review, no cost. No automatic update is documented for a CLI-installed app; assume each release
  is another `homey app install`. That suits the owner and a few technical users of a self-hosted project.
- **Test channel.** `homey app publish` uploads a draft; in Athom's developer tools it can be released to
  **Test**, reachable through a test link only, before any review
  ([Publishing](https://apps.developer.homey.app/app-store/publishing)). Whether a Test release needs
  certification first is not clear: the page says never-released apps "need to be certified before becoming
  publicly available", and Test is not public. Worth trying; it would give auto-updates to testers.
- **App Store (Homey Pro).** Free for developers and users ("Publishing apps for Homey Pro does not require a
  subscription and will always remain free"); apps must be free. Review takes up to two weeks. Requirements that
  matter here ([Guidelines](https://apps.developer.homey.app/app-store/guidelines)):
  English required, no spelling errors, plain-text `README.txt` with no URLs, an app name of at most four words
  without "Homey" or "Athom" (so "Calvin", not "Calvin for Homey"), a one-line description that is not "Adds
  support for…", a 960×960 transparent vector app icon and a different driver icon (Athom draws icons on request
  in its homey-vectors repo), app images 250×175 and 500×350 that are not just a logo, a `brandColor`, only the
  permissions the app needs (the Calvin app needs none), discovery instead of typed addresses where possible, and
  no duplicate app for the same purpose. `homey app validate --level publish` checks the mechanical part.
- **Pick:** CLI install first; App Store once mDNS and the pairing code exist. Both can live side by side: the
  store build is the same app at a higher version.

**Where the code lives.** A new public repo, **`calvin-homey`**. A Homey app is a Node project with its own
manifest, assets, CLI, release flow and store identity (`id` is a reversed domain, for example
`app.calvin.homey` or one under the owner's domain; question 3). It is not a Calvin plugin (calvin-plugins holds
Python code that runs inside Calvin), and putting a Node toolchain into the calvin repo would add a third CI
stack to a public repo for something most users never install.

**Testing and release.** `homey app add-github-workflows` copies Athom's validate, version and publish actions;
CI runs `homey app validate --level publish`, `tsc`, a linter and unit tests. The `homey` module is provided by
the Homey at runtime, so unit tests stub it (driver, device, settings and flow APIs) and drive the Calvin client
against a fake HTTP server built from Calvin's `openapi.json` contract snapshot. Version the app on its own
semver, and declare the oldest Calvin API it needs in the README; at pairing it reads `v` from mDNS (or from a
small version route) and says "Calvin is too old" in plain words instead of failing later. Publishing with
`HOMEY_PAT` from CI is possible later; start manually.

## 6. Fit with the calvin-plugins Homey plugin

The plugin (draft PR 35 in calvin-plugins) shows chosen Homey devices as tiles on a Calvin screen, reading and
switching them through the Homey Pro local Web API with a Homey API key the user creates.

Could the app replace it, by pushing chosen device states into Calvin? It would need:

- `homey:manager:api` in the app, to read and control other apps' devices. Athom says this permission gives
  "complete control over the Homey", is for "Tools" apps, is reviewed "more carefully", and apps that request it
  without need are rejected ([Permissions](https://apps.developer.homey.app/the-basics/app/permissions)). A
  screen-switching app would no longer be a small, obviously safe app.
- A new Calvin write route and storage for pushed device states, a second key permission, and a way for a tap
  on a Calvin tile to reach the Homey again (a command queue the app polls, or the event stream in reverse).
- The tiles would stop working whenever the app is missing, while the plugin works with any Homey Pro, store app
  or not.

What it would remove: the Homey API key stored in Calvin, and Calvin's polling of the hub. That is not enough.
**Keep the plugin.** Two small links are worth it later: the app can show "Calvin also has a Homey plugin"
in its README, and the plugin's settings can link to the app's docs. Revisit only if Athom's local API key
creation turns out to be hard for users (the plugin's own notes mark it "not documented").

## 7. Security

- **Where the key lives.** In the app's `ManagerSettings` on the Homey, readable by the app's code. It is no
  longer in a flow card, where today anyone who can edit flows can read it
  ([HOME_AUTOMATION.md](../integrations/HOME_AUTOMATION.md#security-notes)), which is the main security gain of an
  app. Who else can read app settings through Homey's own Web API (for example other household users, or an
  app with `homey:manager:api` such as a script app) is not documented; assume any Homey owner-level user and
  any "Tools" app on that Homey can. Whether app settings are included in Homey's cloud backups is not
  documented. The app must never show the key again after pairing (show the key prefix only), never log it, and
  never put it in an error.
- **Plain HTTP on the LAN.** Same as today: a device that can watch traffic can copy the key from a request. The
  app should accept an `https://` address and verify its certificate, and say so in its README. A long-lived event
  stream does not change the exposure; the key is sent once per connection instead of once per poll.
- **A leaked key** can switch screens on, off or back to schedule, up to 30 changes a minute, and read what any
  anonymous caller can (`api_keys.py:34-40`, `route_policy.py:359-378`). It cannot change settings, read backups
  or reach MCP or host actions. A pairing-code key (section 3) would be the same kind of key.
- **Revoking.** Revoke in Settings › Security › API keys; the next request fails with `401` because the key file
  is read on every request (`api_keys.py:102-103`). The app should then mark every screen unavailable with
  "Calvin refused the key. Repair a screen to enter a new one." and stop polling until repaired. Uninstalling the
  app deletes its settings on the Homey; the key stays valid in Calvin until revoked, so the README should say to
  revoke it.
- **Homey-side secret.** None in the recommended design: polling and the event stream are both opened by the
  Homey. A webhook design would add a shared secret on both sides; that is one reason not to choose it.
- **Presence.** Unchanged: screen holds are already public reads. The app adds nothing to it.

## 8. Plan sketch

**First version (CLI install, no Calvin change).** About 3 to 5 days, plus the owner's Homey time.

1. Scaffold `calvin-homey` with `homey app create` (TypeScript, Homey Pro only, `compatibility >=12.9.0`),
   Athom's GitHub workflows, lint, `tsc`, unit-test runner, a stub of the `homey` module.
2. Calvin client: list screens, read one screen's power, set power; `Authorization: Bearer` header, 5 s timeout,
   plain-words errors, never logs the key or address. Tested against a fake server shaped by `openapi.json`.
3. Driver *Calvin screen*: custom pairing view (address and key, tested with `GET /api/kiosks` and a warning for
   an admin key), then `list_devices` of screens not yet paired; repair view that changes the connection for all
   screens. **Risky:** custom pairing views and repair are the least documented part.
4. Device: `onoff` listener → `PUT`; poller every 30 s per server updating `onoff`, `calvin_held`,
   `alarm_calvin_offline` and warnings; unavailable on `401`/unreachable. **Risky:** mapping `desiredOn` while a
   command is in flight (read back the `PUT` answer, do not wait for the next poll).
5. Flow cards: "Return to its schedule", "is held", app-level "all screens" actions; English titles and hints.
6. README for users (install with the CLI, create the key, pair), placeholder icon and images.
7. **Needs the owner's Homey:** install, pair, switch from the tile and from a flow, check every trigger and
   condition fires, revoke the key and repair, reboot the Homey. This also answers the open question in
   HOME_AUTOMATION.md about the Bearer header from a Homey, since the app sets the header itself.

**Calvin additions, later.** About 4 to 6 days together.

8. Optional, small: `GET /api/auth/key` (who am I) and bulk `GET /api/kiosks/screen-power`; contract snapshot and
   `types.ts` regenerated. Half a day to a day.
9. mDNS advertisement with a stable server id and API version. **Risky:** Docker networking and the Pi host;
   1 to 2 days.
10. Pairing code: "Connect Homey" in Settings, a one-time short-lived code, the public exchange route that
    creates a limited key. **Risky:** a new unauthenticated write in `security/`; needs its own design doc first.
    1.5 to 2 days.
11. Event stream for screen-power changes and online/offline. 1 to 2 days, then the app switches from polling.
12. Docs: a "Homey app" section in HOME_AUTOMATION.md beside the raw web request steps.

**App Store release.** After 9 and 10: real icons and images, `README.txt`, `validate --level publish`, a Test
release for a few users, then certification (up to two weeks). 1 to 2 days of work plus Athom's review.

**Testable without a Homey:** manifest validation, TypeScript, the Calvin client, the pairing and poll logic
against a stubbed `homey` module and a fake Calvin, and every Calvin-side route in Calvin's own tests.
**Needs a real Homey:** pairing and repair views, the device tile, flow cards firing, behaviour across a Homey
reboot or app update, mDNS discovery on the real network, and a long-lived connection's lifetime.
