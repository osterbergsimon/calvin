# dd9.4 — Per-kiosk content assignment (available screens + default screen) — design

- **Date:** 2026-07-12
- **Status:** Approved (brainstorm), pending implementation plan
- **Issue:** `calvin-dd9.4` (epic `calvin-dd9`)
- **Base branch:** `develop` (this design lives on `feature/dd9.4-per-kiosk-content`)
- **Builds on:** dd9.2 (kiosk identity), dd9.3 (per-kiosk override store + effective-config endpoint). Whole-epic model: [2026-07-11-per-kiosk-settings-model-design.md](2026-07-11-per-kiosk-settings-model-design.md).

## Problem

A kiosk shows one of several **screens** from a global catalog (`dashboardScreens = {version, activeScreenId, screens[]}`). Two gaps block multi-kiosk use:

1. **No per-kiosk assignment:** every kiosk shows the same screens; you can't say "the kitchen Pi shows only the calendar screen, the hallway Pi boots into the agenda screen."
2. **The active screen is *global* and persisted.** Switching screens — keyboard `screen_jump` (`useKeyboardActions.js` `saveDashboardScreens`) or the `ScreenDots` switcher (`config.js` `activateDashboardScreen`/`cycleDashboardScreenBy`) — calls `updateConfig({ dashboardScreens })`, writing `activeScreenId` into **global** config. In Mode B, switching on one kiosk changes the active screen for **all** kiosks.

dd9.4 delivers per-kiosk content assignment and fixes (2), which is a prerequisite: without it, any screen switch clobbers the per-kiosk assignment.

## Decisions

- **Runtime active screen is client-local in Mode B** (kiosk id present): seeded on load, updated on switch, **never written to the server**. Mode A (no id) keeps today's global-persist behavior exactly. (Decision A.)
- **Two override keys** carry the assignment; they flow through dd9.3's effective-config merge with no new endpoints:
  - `availableScreens: list[str] | None` — allowlist of screen ids this kiosk may show (absent/`null` ⇒ all).
  - `defaultScreenId: str | None` — the screen this kiosk boots into.
- **The screen catalog stays global** (authored once in `DashboardRegionsEditor`). dd9.4 only *selects/filters*, never forks the catalog.
- **Setting the keys is via the API** (`PUT /api/kiosks/{id}/overrides`, dd9.3). The friendly admin UI is the deferred management-UI slice, not dd9.4.

## Design

### 1. Backend — type the two keys (2-line change)

Add to `ConfigUpdate` in `backend/app/api/routes/config.py`:
```python
availableScreens: list[str] | None = None
defaultScreenId: str | None = None
```
This lets `PUT /api/kiosks/{id}/overrides` type-check them (dd9.3 validates the override body via `ConfigUpdate`). They already merge into the effective config via dd9.3's shallow merge and are served on `GET /api/kiosks/{id}/config`. No new endpoint, no migration.

### 2. Frontend — local active screen that survives polling (the meat)

The config store polls the effective config every `configPollInterval` (~30s) and re-applies it. A naive "switch mutates `dashboardScreens` locally" would be **clobbered on the next poll**. So the active screen becomes a dedicated local ref, seeded once, preserved across polls, in Mode B.

In `frontend/src/stores/config.js`:
- Add a local `kioskActiveScreenId` ref (null in Mode A).
- **Kiosk mode** = `getKioskId() != null` (reuse dd9.2's `kioskId.js`).
- **Seeding** (once, on first successful config load in kiosk mode): `kioskActiveScreenId = firstValid(defaultScreenId, dashboardScreens.activeScreenId, firstAvailableScreenId)` — see fallbacks below.
- **`applyConfigPayload` must NOT overwrite `kioskActiveScreenId`** on subsequent polls (only seeds when still null). This is the key guard: server `dashboardScreens.activeScreenId` seeds but never re-steers a kiosk that has since switched.
- An **`effectiveActiveScreenId` getter:** kiosk mode ⇒ `kioskActiveScreenId`; Mode A ⇒ `dashboardScreens.value.activeScreenId` (today's source of truth).
- **Switch actions branch on kiosk mode:**
  - `activateDashboardScreen(id)` / `cycleDashboardScreenBy(dir)`: **kiosk mode** ⇒ update `kioskActiveScreenId` locally, **no `updateConfig`**; **Mode A** ⇒ unchanged (mutate `dashboardScreens` + `updateConfig`). The keyboard path (`useKeyboardActions.js` `saveDashboardScreens` / `activateFirstScreenContainingKind`) routes through the same store actions so it inherits the branch.
- Components that read the active screen (`ClockBarHorizontal`/`Vertical` via `getActiveDashboardScreen`, `Dashboard.vue`, `ScreenDots`) consume `effectiveActiveScreenId` (the store getter) instead of reading `dashboardScreens.activeScreenId` directly.

### 3. `availableScreens` filtering + seeding + fallbacks

- **Filtering (kiosk mode):** the switcher's visible screens = `dashboardScreens.screens` filtered to `availableScreens` (absent ⇒ all). `ScreenDots` renders only the allowed set; keyboard `screen_jump`/cycle actions skip disallowed screens. A kiosk cannot switch to a screen it isn't assigned.
- **Seed precedence** for `kioskActiveScreenId`: `defaultScreenId` → else global `dashboardScreens.activeScreenId` → else first available screen.
- **Fallbacks (never render an empty/invalid screen):**
  - `defaultScreenId` not in `availableScreens`, or not in the catalog ⇒ fall back to the first available screen.
  - `availableScreens` lists ids absent from the catalog ⇒ ignore those ids (intersect with the catalog).
  - `availableScreens` empty or resolves to nothing valid ⇒ treat as "all" (fail open — a blank kiosk is worse than an over-broad one).
  - If the current `kioskActiveScreenId` is no longer available (catalog edited server-side, picked up on poll) ⇒ re-seed to the first available.
- Pure helpers (in `frontend/src/utils/layout.js`, next to the existing screen helpers) so this logic is unit-testable without a store: e.g. `filterAvailableScreens(screens, availableIds)` and `resolveKioskActiveScreen({screens, availableScreens, defaultScreenId, current})`.

## Data flow

```
GET /api/kiosks/hallway-1/config  (dd9.3)
  → effective config incl. { dashboardScreens (global catalog),
                             availableScreens?: [...], defaultScreenId?: "screen-agenda" }
  → config store: kiosk mode → seed kioskActiveScreenId once (default→global→first-available),
                  filter switcher to availableScreens
  → user presses screen_jump / taps ScreenDot:
       kiosk mode → kioskActiveScreenId = next allowed id  (LOCAL, no server write)
  → next 30s poll re-applies config → kioskActiveScreenId preserved (guard), catalog refreshed
Mode A (no kiosk id): unchanged — switch persists to global dashboardScreens.
```

## Backward compatibility

- **Mode A** (no kiosk id): every path unchanged — active screen still lives in global `dashboardScreens.activeScreenId`, switches still `updateConfig`. Regression-guarded.
- A kiosk with no `availableScreens`/`defaultScreenId` overrides ⇒ all screens available, boots to the global active screen — i.e. current behavior, just now *local* (a switch no longer leaks to other kiosks).
- The global catalog + `DashboardRegionsEditor` are untouched.

No new endpoint, no migration, no dependency.

## Testing strategy

- **Backend:** `PUT /api/kiosks/{id}/overrides` accepts `availableScreens`/`defaultScreenId` (typed) and they appear in the effective config; a wrong type → 400 (dd9.3 handler).
- **Frontend (pure helpers):** `filterAvailableScreens` (absent ⇒ all; intersect with catalog; empty ⇒ all). `resolveKioskActiveScreen` seed precedence + every fallback (invalid default, stale current, ids not in catalog).
- **Frontend (config store):** Mode-A switch still calls `updateConfig` (regression); kiosk-mode switch updates `kioskActiveScreenId` with **no** network write; a config poll does not clobber a switched `kioskActiveScreenId`; seeding runs once; switcher/keyboard filtered to `availableScreens`.

## Non-goals / deferred

- **Admin UI** to set `availableScreens`/`defaultScreenId` per kiosk — the management-UI slice.
- **Per-kiosk region-view state** (calendar rolling/counts via `updateRegionView`, `cycleActiveDashboardRegionBy`) — these still persist to global in Mode B; localizing them is a separate concern (note as a known limitation, not fixed here).
- **Multi-output** (one Pi → multiple screens) — dd9.5.

## Open questions

None blocking. The region-view-state limitation is called out above as deliberately out of scope; if it proves annoying in practice, it's a small follow-up using the same kiosk-mode-local pattern.
