# dd9.6 — Where 'orientation' lives (decision) + Mode-A guard — design

- **Date:** 2026-07-12
- **Status:** Approved (brainstorm), pending implementation plan
- **Issue:** `calvin-dd9.6` (epic `calvin-dd9`, type: decision)
- **Base branch:** `develop` (this doc lives on `feature/dd9.6-orientation-home`)
- **Relates to:** the whole-epic model
  [2026-07-11-per-kiosk-settings-model-design.md](2026-07-11-per-kiosk-settings-model-design.md);
  builds on dd9.3 (per-kiosk override store).

## Problem

The global server config holds `orientation` / `orientationFlipped` / `applyDisplayRotation`,
applied at backend startup by `display_orientation_service` via `xrandr`. In server+kiosk
(Mode B) this is wrong: orientation is physical to each Pi, but the setting is global and the
*backend* can't reach a remote kiosk's display. This issue decides orientation's canonical home
and precedence, and cleans up the one piece of live code that misbehaves in Mode B.

## Decision (ratified)

- **Canonical home = per-kiosk server config** (an override key), **applied device-side by the
  display-agent.** This is already true at the data layer: `orientation` / `orientationFlipped` /
  `applyDisplayRotation` are fields on `ConfigUpdate` (so dd9.3's `PUT /api/kiosks/{id}/overrides`
  already accepts them) and are in `DEVICE_PHYSICAL_KEYS` (so the `deviceConfigVersion` bumps on an
  orientation change → the display-agent detects it). No new storage/serving work.
- **Precedence:** device-local env (`CALVIN_DISPLAY_ROTATION`, the break-glass escape hatch) **>**
  per-kiosk override (server) **>** global default.
- **Global config keeps `orientation` as a default** — Mode-A single-Pi installs and the template
  new kiosks inherit it. It is *not* removed.

## The one code change — Mode-A guard on the startup sync

`backend/app/main.py`'s `_sync_display_orientation()` calls `display_orientation_service.sync_with_config()`
at startup, which runs `xrandr` on the **backend's** host. Today it guards on `is_raspberry_pi()`
(so a non-Pi Docker server is already quiet) and catches exceptions, but a **Pi acting as a remote
backend with no local X display** still hits `xrandr`, fails, and logs a `warning` every boot — and
the intent ("orient the machine the backend runs on") is wrong in Mode B.

**Change:** gate the startup sync on a **local display actually being present**, reusing the
existing `has_x11()` helper (`app.utils.platform`). If no local X display, **skip at `debug`
level** and return early — do not call the service, do not run `xrandr`. When a local display *is*
present, behavior is unchanged (Mode-A auto-orient-on-boot still works; genuine errors still warn).

Sketch (in `_sync_display_orientation`):
```python
from app.utils.platform import has_x11
if not has_x11():
    logger.debug("No local X display; skipping backend orientation sync (device-side agent owns it in Mode B)")
    return
# ... existing apply_rotation / sync_with_config logic unchanged ...
```

- `display_orientation_service` itself (`get_current_orientation` / `apply_orientation` /
  `sync_with_config`) is **kept** — it's still the Mode-A path; it's just no longer invoked
  pointlessly on a display-less backend.
- No new config or env flag: the guard auto-adapts (local display ⇒ Mode-A behavior; none ⇒ skip).

## Settings UI orientation control

**Keep as-is.** It writes the **global default** orientation (a Mode-A convenience and the template
new kiosks inherit). Per-kiosk orientation is set via the API (`PUT /api/kiosks/{id}/overrides`)
today; a friendly per-kiosk control is part of the deferred management-UI slice, not dd9.6.

## Affected code

| Area | Path |
|---|---|
| Mode-A guard on startup sync | `backend/app/main.py` (`_sync_display_orientation`) |
| Reuse local-display check | `app.utils.platform.has_x11` (existing) |
| Test | `backend/tests/` (unit test for the guard) |

No migration, no new dependency, no API change. Orientation override storage/serving already
shipped in dd9.3.

## Testing strategy

- **Unit:** `_sync_display_orientation` (or an extracted testable unit) — when `has_x11()` is
  **False**, it returns early without calling `display_orientation_service.sync_with_config`
  (assert the service is not invoked; assert a debug-level, not warning-level, log). When
  `has_x11()` is **True**, it proceeds to the existing sync path (service called). Patch `has_x11`
  and the service to assert the branch.

## Follow-ups (file, don't build here)

1. **Display-agent applies orientation** from the merged per-kiosk config (read `orientation`/
   `orientationFlipped` from `GET /api/kiosks/{id}/config`, apply via `xrandr`, honor the
   `CALVIN_DISPLAY_ROTATION` env escape hatch as the winning layer). This is part of the deferred
   **display-agent-apply** slice (kin to dd9.1 follow-ups) — verify it's captured, file if not.
2. **Per-kiosk orientation control** in the eventual management UI (set a kiosk's orientation
   override without curl) — part of the deferred management-UI slice.

## Open questions

None. The decision is ratified and the storage/serving already exists; dd9.6's only build is the
