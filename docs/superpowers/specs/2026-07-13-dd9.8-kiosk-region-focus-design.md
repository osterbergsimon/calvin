# Kiosk region-focus targets the effective active screen — design

- **Date:** 2026-07-13
- **Status:** Approved (brainstorm), pending implementation plan
- **Issue:** `calvin-dd9.8` (BUG — kiosk region-focus targets global active screen; read/write asymmetry). Discovered in the dd9.4 whole-branch review.
- **Base branch:** `develop` (this design lives on `feature/dd9.8-region-focus`)

## Problem

In kiosk mode the active **screen** is local (`kioskActiveScreenId`), and reads honor it —
`getActiveRegion()` resolves through `effectiveDashboardScreens` (which overrides `activeScreenId` with
`kioskActiveScreenId` in kiosk mode). But the region-focus **writes** don't: `cycleActiveDashboardRegionBy`,
`updateRegionView`, `focusRegion`, and the `region_next`/`region_prev` keyboard actions all pass the raw
global `dashboardScreens.value` to layout helpers that locate the active screen from
`screensConfig.activeScreenId` (the global field). When the kiosk's local active screen differs from the
global one, region navigation operates on — and persists a region bookmark for — a screen the operator
isn't looking at. The bug is data-loss-safe (no screens dropped); it is a latent UX quirk: "next region"
appears to do nothing because it moved the focus on a different screen.

## Root cause (verified in develop)

- `effectiveDashboardScreens` (config store) resolves the active screen correctly in both modes: Mode A →
  the normalized global `activeScreenId`; kiosk → `kioskActiveScreenId ?? filtered.activeScreenId`.
- Reads use it (`getActiveRegion` in `useKeyboardActions.js`).
- Writes do **not**. The layout locators — `getActiveDashboardScreen`, `setActiveDashboardRegion`,
  `cycleActiveDashboardRegion`, `setRegionView` (in `utils/layout.js`) — find the active screen only via
  `screensConfig.activeScreenId`, with no way to override it. The store/composable write paths hand them the
  raw config, so they target the global active screen.
- Region writes persist **globally** (`updateConfig({ dashboardScreens })`) in both modes — unlike screen
  *selection* (`setActiveDashboardScreen`/`cycleDashboardScreen`), which is kiosk-local. Region state being
  global was an explicit dd9.4 non-goal; this design keeps that.

## Fix — thread the effective active-screen-id through the write helpers (approach A)

The read path already resolves the right screen. Give the write helpers the same id, so the mutation lands
on the screen the operator sees, while the persisted config's own `activeScreenId` is left untouched (we
change only that screen's `activeRegionId` / region `view`, not which screen is globally active).

### `frontend/src/utils/layout.js` — optional `activeScreenId` param

Add an optional trailing `activeScreenId` parameter to the four locators; when omitted or falsy, fall back
to the config's own `activeScreenId` — so every existing (Mode-A) caller is byte-for-byte unchanged.

- `getActiveDashboardScreen(screensConfig, activeScreenId = null)` — resolve the target screen as
  `screens.find(s => s.id === (activeScreenId || normalized.activeScreenId)) || screens[0]`.
- `setActiveDashboardRegion(screensConfig, regionId, activeScreenId = null)` — locate the screen via the
  passed id (through `getActiveDashboardScreen`), mutate that screen's `activeRegionId`.
- `cycleActiveDashboardRegion(screensConfig, direction = 1, activeScreenId = null)` — find the screen index
  by the passed id, cycle its `activeRegionId`.
- `setRegionView(screens, regionId, patch, activeScreenId = null)` — operate on
  `screens.find(s => s.id === (activeScreenId || next.activeScreenId)) || screens[0]`.

None of these change the returned config's `activeScreenId`; they only edit the located screen's
region state.

### `frontend/src/stores/config.js` — pass the effective id

- `cycleActiveDashboardRegionBy(direction)`:
  `cycleActiveDashboardRegion(dashboardScreens.value, direction, effectiveDashboardScreens.value.activeScreenId)`.
- `updateRegionView(regionId, patch)`:
  `setRegionView(dashboardScreens.value, regionId, patch, effectiveDashboardScreens.value.activeScreenId)`.

Persistence is unchanged (still `dashboardScreens.value = next; await updateConfig({ dashboardScreens: next })`).

### `frontend/src/composables/useKeyboardActions.js` — pass the effective id

- `region_next` / `region_prev`:
  `cycleActiveDashboardRegion(getDashboardScreens(), ±1, configStore.effectiveDashboardScreens.activeScreenId)`.
- `focusRegion(regionId)`:
  `setActiveDashboardRegion(getDashboardScreens(), regionId, configStore.effectiveDashboardScreens.activeScreenId)`.

`getActiveRegion` (the read) is already correct and unchanged.

## Data flow (after fix)

```
kiosk mode, global active = A, kiosk active (kioskActiveScreenId) = B, user views B
region_next → cycleActiveDashboardRegion(rawScreens, +1, effectiveActive=B)
            → mutates screen B's activeRegionId (not A's)
            → persist global dashboardScreens (B's activeRegionId changed; global activeScreenId still A)
getActiveRegion → effectiveDashboardScreens (active=B) → reads B's activeRegionId  ✓ symmetric
```

Mode A (`getKioskId()` null): `effectiveDashboardScreens.activeScreenId` equals the global
`activeScreenId`, so the passed id matches the helper's own fallback — behavior is identical to today.

## Error handling / edge cases

- Effective active id points to a screen not present in the raw config (e.g. filtered-out): the helpers'
  `|| screens[0]` fallback keeps them safe (no throw; degrade to the first screen), same as today.
- `effectiveDashboardScreens.activeScreenId` is null/undefined: falsy → helper falls back to the config's own
  `activeScreenId` — identical to current behavior.
- No persistence-path change, so no new server/write risk; the global-region-state decision from dd9.4 is
  preserved.

## Testing strategy

Vitest, mirroring `tests/unit/layout.spec.js`, `tests/unit/utils/layoutSetActiveRegion.spec.js`, and
`tests/unit/stores/config.spec.js`.

**Layout helpers (unit):**
- `cycleActiveDashboardRegion(config, dir, "B")` cycles screen **B**'s active region while the config's
  `activeScreenId` stays `"A"`; omitting the arg still uses `activeScreenId` (existing tests unchanged).
- `setActiveDashboardRegion(config, regionId, "B")` sets region on screen B only.
- `setRegionView(config, regionId, patch, "B")` patches a region-view on screen B only.
- `getActiveDashboardScreen(config, "B")` returns screen B; `getActiveDashboardScreen(config)` returns the
  `activeScreenId` screen (unchanged).

**Store (kiosk-mode regression):**
- With `getKioskId()` truthy, `kioskActiveScreenId = "B"`, global `activeScreenId = "A"`:
  `cycleActiveDashboardRegionBy(1)` changes screen **B**'s `activeRegionId` in the persisted
  `dashboardScreens` (assert on the mocked `axios.post`/`updateConfig` payload), not screen A's; and the
  config's `activeScreenId` is still `"A"`.
- `updateRegionView(regionId, patch)` in kiosk mode patches screen B's region.
- Mode A: `cycleActiveDashboardRegionBy` still targets the global active screen (unchanged).

**Deferred minors from the bead:**
- `resolveKioskActiveScreen` null-return case — add only if it exercises a real branch; if the `?? null` is
  unreachable dead code, note that in the test file instead of writing a vacuous test.
- Store-level Mode-A `cycleDashboardScreenBy` persistence — verify the existing test
  (`config.spec.js` "Mode A: cycleDashboardScreenBy persists via axios.post") covers it; add only if missing.

## Non-goals (follow-ons)

- **Making region focus/view per-kiosk-local** — that reverses dd9.4's explicit "region state is global"
  decision and needs a per-kiosk region-state store; separate slice if ever wanted.
- Any change to screen-**selection** behavior (already correct: kiosk-local, non-persisting).
- Restructuring the layout helpers beyond the optional-parameter addition.

## Open questions

None blocking. Approach A (thread the effective active-screen-id, keep global persistence) was approved in
brainstorming.
