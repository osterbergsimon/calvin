    Kiosk performance profile — Raspberry Pi 3B+ / cog (WPE WebKit)¶

    Date: 2026-11-02 Task: calvin-qpao (phase 1: measure, do not optimise) Scope: the dashboard, not Settings. The owner reports that Settings feels fast while the dashboard feels slow. The profile is weighted towards the dashboard and breaks the cost down per region type.

    TL;DR¶

    • A dashboard tap is not a JavaScript problem. The all-regions tap costs 658 ms of main-thread time, but application JS is only 8 ms. About 90 % is native (program) work — paint, raster and image decode. The same is true for the photo advance (18.9 ms app JS, 558 ms native).
    • The two biggest paint costs are the focus light and the photo backdrop. Every tap turns on a four-layer box-shadow (up to 68 px blur) on the active region and applies filter: saturate() brightness() to every other region. Every photo is drawn twice: a full-size <img> plus a full-size copy with filter: blur(28px) brightness(0.55).
    • The initial bundle is 1.22 MB of JS (≈392 kB gzip) plus 257 kB of CSS. The 630 kB settings chunk and the 378 kB plugins chunk are both loaded on the first dashboard paint, although the dashboard does not need most of either.
    • A photo is downloaded and decoded at 4032×3024 (12.2 MP) for a 626×637 (0.40 MP) box — about 30× more pixels than displayed — and a second full-size <img> copy is rasterized with a 28 px blur for the backdrop. The mock photo is 4.00 MB.
    • Idle is cheap but not quiet. Steady-state idle is 54–160 ms of main-thread work per 30 s (≈0.2–0.5 % of one core), but a 100 ms setInterval fires 300 times per 30 s, a 30 s photo rotation triggers the full 0.74–0.96 s photo advance, and 66 comet-orbit CSS animations exist (paused at idle, running during loads).
    • A "low-power screen" setting would help, because the dominant cost is decorative paint. It can switch off the comet loading light, the focus glow and dim filter, the photo backdrop blur, and lengthen/disable photo rotation. It will not fix the initial bundle or the calendar's forced layout.

    All timings below are from Chromium with Emulation.setCPUThrottlingRate = 6 (the Pi 3 core is roughly 6–10× slower than a desktop core). Treat them as approximations of the Pi, not exact port measurements.

    Method¶

    • Production build (npm run build), served from dist/ by vite preview on 127.0.0.1:4173. The profiling script builds with sourcemaps and a temporary Vite config that exposes the Vue app for component mount/update counters; the repository config is unchanged.
    • Playwright Chromium 143, viewport 1280×720, serviceWorkers: "block".
    • Every /api request is answered by the existing mocked harness (frontend/tests/e2e/phone/fixtures/api-mock.js). Host-acting routes (/api/system/reboot, /restart-*, /update, /display/*, …) are intercepted and recorded; hostActions is empty in every run. No real backend is contacted.
    • Realistic mock data: two/three dashboard screens; a calendar with 22 timed and all-day events; five 4032×3024 photos (4.00 MB each); the horizontal clock bar at the top; showUI: true, focus light on interaction, dim-others on, 30 s photo rotation, 30 s config poll.
    • Measurements:
    • CDP Performance.getMetrics() for TaskDuration, ScriptDuration, RecalcStyleCount/Duration, LayoutCount/Duration;
    • CDP Profiler (500 µs sampling) for self time, symbolised through the production sourcemaps to frontend/src/...:line;
    • PerformanceObserver({ entryTypes: ["longtask"] }) for tasks > 50 ms;
    • a Vue mixin in the profiling build for per-component mount/update counts;
    • wrapped setInterval/setTimeout/requestAnimationFrame for the idle timer inventory, with stacks symbolised to source.
    • Caveats: Chromium, not cog/WPE WebKit. Paint and raster behaviour differs; the Pi's GPU may make some effects cheaper and others more expensive. Mock data is not the owner's real library. Run-to-run variance was ±20–30 % (initial load ranged 1.58–2.24 s across runs). The iframe region is a mocked external page and is not present on the owner's real dashboard; it was measured briefly. The unauthenticated Settings lock screen crashes the production renderer in this harness, so the OSK was measured on the Settings search field instead.

    Reproduce:

    cd frontend
node scripts/profile-kiosk.mjs --out /tmp/opencode/kiosk-profile.json

# reuse an existing build/preview
node scripts/profile-kiosk.mjs --skip-build --base-url http://localhost:4173 \
  --only initial-load,photo-advance,page-switch-calendar-photos

    The script prints a summary and writes the raw JSON (scenario metrics, profiles, timer stacks, bundle list) to the --out path.

    What changes in the other regions:

    • A tap on the calendar re-renders the photos region three times and the clock bar twice, even though neither changed. focusRegion (useKeyboardActions.js:1031) calls saveDashboardScreens, which posts the whole dashboardScreens config through updateConfig (:67-76). The response replaces the config payload and re-renders every region. activeRegionId is screen state, not a global setting, and should not be persisted on every tap.
    • Advancing a photo re-renders the calendar four times and the clock bar three times. The same full-config write is involved (focusing the photo region before the advance), plus the photo store update.
    • A page switch unmounts and remounts every region component (46 unmounted, 41 mounted in the all-regions layout). That is where the 119 ms layout and the 90–126 ms measureHeaderWidth go: 20 CalendarTimedEvent and 3 CalendarRibbon components are created again.
    • Idle cost is mostly timers, not region rendering. The isolated idle runs are 54–160 ms per 30 s. The photos-only idle is higher because the 30 s rotation fires at the edge of the window; the real cost of that rotation is the photo-advance measurement (0.74–0.96 s).
    • The clock bar itself is cheap (tap 482 ms with app JS 1.9 ms; idle 54 ms). It is the focus light / paint path that makes even the clock-bar tap expensive.

    requestAnimationFrame¶

    Zero callbacks during idle. There is no rAF loop on the dashboard. (The interaction runs use Playwright's waitForFunction polling, which does use rAF; that is harness traffic, not app traffic.)

    CSS animations and transitions¶

    • 66 paused comet-orbit CSSAnimations: 22 CometIndicator beads × 3 LoadingLight frames (app frame + calendar region + photos region). In the calendar-only or clock-bar-only layout there are 44 (app + one region). animation-play-state: paused is working: playState is paused and there is no animation work at idle. During a load, the same 66 elements animate offset-path and paint three box-shadow layers each.
    • No running CSS transitions at idle. The focus-light and panel transitions finish within 200 ms of the last input.
    • No animated gradients. The gradients in FocusPanel.vue:40-42, DashboardPanel.vue:100-104 and the between-bar are static; color-mix() in them is resolved during style recalc, not animated.
    • The 30 s photo rotation and 30 s config poll each fire once per idle window and account for the 13 Vue updates (CalendarView, PhotoSlideshow, ClockBar, DashboardRegion, ScreenDots, FocusPanel, RegionHeaderControls, CalendarViewOptions).

    Would a "low-power screen" setting help?¶

    Yes. The measurements show the dashboard's per-interaction cost is dominated by decorative paint, not application JS (tap: 8 ms app JS vs 570 ms native program). A per-screen preset can remove most of that paint without touching the data model.

    It should switch off:

    • Loading light → off (or pulse): removes the 22-bead comet with three box-shadow layers and offset-path animation on the app frame and each region.
    • Focus light → off, and dim others → false: removes the 68 px four-layer glow and the filter: saturate() brightness() transition on every non-active region.
    • Photo backdrop → force fill (or a new "no backdrop" option): removes the second full-size layer and the 28 px blur.
    • Photo rotation → 5–15 min, or only while the screen is awake: removes the 0.74–0.96 s spike every 30 s.
    • On-screen keyboard → off on kiosks that use a remote/keyboard, and/or lazy-load it so simple-keyboard is not in the initial graph.
    • Decorative motion → a data-low-power class (or reusing the prefers-reduced-motion rules) that sets animation: none, transition: none, filter: none, backdrop-filter: none for non-essential chrome.
    • Clock seconds → keep off (already the default); if on, it re-renders the clock every second.

    It will not fix:

    • the 1.22 MB initial JS / 630 kB settings + 378 kB plugins chunks (fixes 3–4);
    • the calendar's forced layout and event formatting (fix 6);
    • the full-config write that re-renders unrelated regions (fix 5);
    • the 12 MP photo decode unless photos are also resized (fix 1).

    A low-power preset is therefore a useful mitigation (estimated 40–60 % of the tap/page-switch paint cost and most of the photo cost if combined with resized photos), but not a substitute for the bundle, photo-resize and focus-light code fixes.

    Other findings / follow-ups¶

    • The photo next/previous buttons are under the image for hit-testing. Playwright's click on .photo-slideshow [data-action="next"] is intercepted by img.photo-image: the header overlay and the photo both use --z-raised, and the photo is later in the DOM. The profiling script drives the handler directly, but a real tap on the arrow may do nothing. This looks like a real hit-testing defect worth a separate issue with a small z-index/stacking fix in DashboardPanel.vue/PhotoSlideshow.vue.
    • The unauthenticated Settings lock screen crashes the production renderer in this harness (#auth-signin-password never appears; the target crashes). The existing e2e OSK spec runs against the dev server and passes, so this may be a production-build/harness interaction rather than a user-facing bug; it was not investigated further in this measurement task.
    • simple-keyboard and vuedraggable are in the initial graph (43.7 ms and 14.3 ms of self time) even though the dashboard does not use them. This is part of fixes 3, 4 and 9.
    • configPollInterval is 30 s and each poll replaces the whole config payload, causing 13 component updates in an otherwise idle window. If the payload is unchanged, skip the reactive write.
