    dd9.3 — Server-side per-kiosk config store + per-kiosk config endpoints — design¶

    • Date: 2026-07-12
    • Status: Approved (brainstorm), pending implementation plan
    • Issue: calvin-dd9.3 (epic calvin-dd9)
    • Base branch: develop (this design lives on feature/dd9.3-per-kiosk-config)
    • Builds on: dd9.2 (kiosk identity). The whole-epic model is in 2026-07-11-per-kiosk-settings-model-design.md; this doc pins the dd9.3-specific decisions.

    Problem¶

    dd9.2 gave each kiosk a stable identity and a registry (kiosks table with an unused overrides JSON column + last_applied_version, and GET /api/kiosks). Today the kiosk carries its id as ?kiosk=<id> on GET /api/config, which only records the kiosk and returns global config unchanged. This slice adds the per-kiosk config layer: a place to store sparse overrides per kiosk, a way for each kiosk to read its effective (merged) config, and a cheap version signal the (future) display-agent will poll to know when to re-apply device-physical settings.

    API shape (decision: consolidate under /api/kiosks/{id})¶

    The per-kiosk surface lives entirely under /api/kiosks/{id}; /api/config goes back to meaning only "global". Exactly one endpoint per persona:

    Endpoint Persona Returns / does
    GET /api/config Mode-A Pi / no identity Global config (also the template kiosks inherit). Unchanged.
    GET /api/kiosks/{id}/config client (browser + display-agent) That kiosk's effective (merged) config. Records the kiosk. ETag + 304.
    GET/PUT /api/kiosks/{id}/overrides admin (future UI / curl) The raw sparse override layer.

    "Effective config" (the computed result a client runs) and "the override layer" (the sparse thing an admin edits) are genuinely different resources — not a query-param toggle on /api/config. This retires the ?kiosk=/?khost= params on /api/config: a kiosk now registers itself by fetching its own config endpoint.

    Goals¶

    • Store a sparse per-kiosk override layer; read/write it via GET/PUT /api/kiosks/{id}/overrides.
    • GET /api/kiosks/{id}/config returns shallow-merge(global, overrides[id]) and records the kiosk (last-seen, ?khost= hostname).
    • Expose a deviceConfigVersion (ETag + body field) on the effective-config read so the future agent can detect device-physical changes cheaply.
    • Backward compatible for Mode A: GET /api/config (no id) is byte-identical to today.
    • A kiosk with no overrides ⇒ its effective config == defaulted global (plus the version field).

    Non-goals (deferred)¶

    • The display-agent apply loop (read device-physical, xrandr/backlight, If-None-Match fast-poll, POST back last_applied_version) — its own later slice, merges with dd9.1. This slice is testable with API + unit tests, no Pi.
    • Content-assignment keys (availableScreens, defaultScreenId) — dd9.4; just more override keys, no new mechanism.
    • The admin write UI — a later slice once the backend is complete.

    Design¶

    1. Storage — reuse KioskDB.overrides¶

    The overrides JSON column already exists (dd9.2). It holds a sparse dict of config fields, e.g. {"orientation": "portrait", "displayScheduleEnabled": true}. No migration. null/absent ⇒ no overrides.

    2. DRY refactor — extract the global-config builder¶

    get_config in backend/app/api/routes/config.py builds the global dict then applies ~150 lines of inline defaults. The effective-config endpoint needs the same defaulted global as its merge base, so extract that into a reusable helper rather than duplicating it:

    • async build_global_config() -> dict (in config_service or a config route helper) — returns the fully-defaulted global config (including frontendVersion, devMode).
    • GET /api/config becomes a thin wrapper: return await build_global_config(). Its kiosk/ khost params are removed (retired).

    3. Effective-config read — GET /api/kiosks/{id}/config¶

    The single endpoint a client (browser + agent) reads in Mode B.

    1. Validate {id} against _KIOSK_ID_RE (^[A-Za-z0-9._-]{1,64}$, reuse from kiosk_registry); 400 on bad shape.
    2. Record the kiosk best-effort: record_kiosk(id, hostname=khost) (from ?khost=<host>), wrapped in try/except + logger.warning (same hardening as dd9.2's config recording).
    3. base = await build_global_config(); overrides = await get_overrides(id); merged = merge_overrides(base, overrides) (shallow top-level: each override key replaces that global key; no recursion, no array merge).
    4. version = device_config_version(merged); attach as body field deviceConfigVersion and as an ETag header. If the request's If-None-Match equals version, return 304 Not Modified (no body).
    5. Merged config includes device-physical values (served, not stripped) — the agent reads them; the browser ignores what it can't act on in Mode B.

    An unknown kiosk id here is not an error: it records the kiosk and returns defaulted global + version (a kiosk's first-ever fetch registers it). Invalid shape is a 400.

    4. Override layer CRUD — GET/PUT /api/kiosks/{id}/overrides¶

    • GET → {"id": <id>, "overrides": {...}} — the raw stored layer (NOT merged). 404 if the kiosk id is unknown (you can't read overrides of a kiosk that doesn't exist). 400 on bad id shape.
    • PUT body {"overrides": {...}} → replaces the whole layer (idempotent; the editor does read-modify-write). PUT {"overrides": {}} clears. Upserts the kiosk row if new (pre-provisioning). 400 on bad id shape or malformed body. Wrap the write with retry_on_db_locked.
    • Validation: the overrides object is validated by the existing ConfigUpdate model (extra="allow" — unknown keys pass, declared keys type-checked). Reject a non-object body; cap serialized size (reject > 64 KB). No hand-maintained per-kiosk allowlist — the UI controls which fields it exposes.

    5. deviceConfigVersion — ETag + body field¶

    • DEVICE_PHYSICAL_KEYS — a module constant naming the keys a device-agent applies: orientation, orientationFlipped, applyDisplayRotation, displayScheduleEnabled, displaySchedule (current), plus reserved displayBrightness, displayOutput, displayResolution (harmless if absent). One place to extend as dd9.1 follow-ups land.
    • Version = short hex of sha256(json.dumps({k: merged.get(k) for k in DEVICE_PHYSICAL_KEYS}, sort_keys=True, default=str)). Stable (sorted keys); any device-physical change ⇒ new version; theme/time-format changes do not bump it.

    6. Service layer (app/services/kiosk_registry.py)¶

    Pure functions (DB-free, unit-testable) + thin DB accessors: - def merge_overrides(base: dict, overrides: dict | None) -> dict — shallow top-level merge. - def device_config_version(merged: dict) -> str — the hash helper. - async get_overrides(kiosk_id) -> dict | None — raw layer, None if kiosk unknown. - async set_overrides(kiosk_id, overrides: dict) -> None — upsert row + replace overrides (retry_on_db_locked). - record_kiosk / list_kiosks — reuse from dd9.2.

    7. Frontend — withKiosk becomes a URL selector¶

    dd9.2's withKiosk() appended ?kiosk=&khost= to /api/config. Change it to a URL selector so a scoped client fetches its own endpoint: - frontend/src/utils/kioskId.js: replace withKiosk(url) with configUrl() — when getKioskId() is set, return /api/kiosks/{id}/config?khost=<encoded host>; else /api/config. - frontend/src/stores/config.js: the GET uses configUrl(). The POST stays axios.post("/api/config", ...) = global (per-kiosk override writes are the future admin UI via PUT /api/kiosks/{id}/overrides, not the config store's normal save).

    This keeps the frontend change small and contained (it's our own unreleased dd9.2 code).

    Data flow¶

    Browser / display-agent  (Mode B, has id)
  └─ GET /api/kiosks/hallway-3f9a2c/config?khost=pi-hallway   [If-None-Match: <etag>?]
        └─ validate id shape
        └─ record_kiosk(id, hostname=khost)          (best-effort)
        └─ base    = build_global_config()           (shared with /api/config)
        └─ overrides = get_overrides(id)
        └─ merged  = merge_overrides(base, overrides)   (shallow)
        └─ version = device_config_version(merged)
        └─ If-None-Match == version ? 304 : 200 + ETag + body{..., deviceConfigVersion}

Mode-A Pi / no identity
  └─ GET /api/config → build_global_config()          (global, unchanged)

Admin UI (future) / curl
  └─ GET /api/kiosks/{id}/overrides  → { id, overrides }
  └─ PUT /api/kiosks/{id}/overrides  { overrides:{...} } → upsert + replace

    Backward compatibility¶

    • Mode A: GET /api/config (no id) is byte-identical to today (regression test).
    • dd9.2 recording relocates: the ?kiosk=/?khost= params + recording move off /api/config onto GET /api/kiosks/{id}/config. dd9.2's recording integration tests are updated/relocated to the new endpoint; test_get_config_no_kiosk_unchanged becomes the Mode-A regression guard.
    • New kiosk / no overrides ⇒ effective config == defaulted global (plus deviceConfigVersion).
    • POST /api/config stays global-only (unchanged).

    Affected code¶

    Area Path
    Extract build_global_config; GET /api/config → global-only (drop kiosk params) backend/app/api/routes/config.py
    Effective-config + override CRUD routes backend/app/api/routes/kiosks.py
    Service: overrides + merge + version helpers backend/app/services/kiosk_registry.py
    Reuse id-shape regex / ConfigUpdate validation kiosk_registry.py / config.py
    Frontend URL selector frontend/src/utils/kioskId.js, frontend/src/stores/config.js
    Tests backend/tests/unit/test_kiosk_registry.py, backend/tests/integration/test_api_config.py, test_api_kiosks.py, frontend/tests/unit/kioskId.spec.js
    Docs docs/setup/DEPLOYMENT_TOPOLOGIES.md (kiosk-identity section → per-kiosk config + endpoints)

    No migration (column exists). No new dependency. OpenAPI snapshot + generated types.ts regenerate (additive: new kiosk endpoints, /api/config loses its query params).

    Testing strategy¶

    • Unit (pure, no DB): merge_overrides — override wins, sparse fall-through, empty/None == base, top-level-only (nested key replaces wholesale). device_config_version — stable for same inputs; bumps on a device-physical key change; unchanged on a non-device-physical change.
    • Service: get_overrides (unknown → None), set_overrides (upsert new kiosk; replace; clear via {}).
    • Integration: PUT then GET /api/kiosks/{id}/overrides round-trip; GET /api/kiosks/{id}/config reflects overrides and records the kiosk; GET /api/config unchanged (Mode-A regression); unknown-kiosk effective == global; ETag present + If-None-Match → 304; invalid id → 400; oversized override body → rejected; POST /api/config still writes global.
    • Frontend: configUrl() returns /api/kiosks/{id}/config?khost=… when an id is present, /api/config when not; config store GET uses it; POST stays /api/config.

    Open questions¶

    None blocking. Deferred by design: the display-agent apply loop (own slice), content-assignment override keys (dd9.4), the write UI (later). The deviceConfigVersion surface (ETag + body field) is deliberately enough for the agent slice without a dedicated version endpoint now.
